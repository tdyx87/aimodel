# 角色设计（第一层）

> 本文档是**角色驱动开发系统**的**角色体系设计**：定义需要哪些职责分工、边界、输入输出与协作关系。
> 角色的可执行定义（工具/提示词/模型绑定）见 `agents/`（第二层）。
> 方法论与全局约定见 `agents.md`。
>
> **设计前提**：本系统面向**面向最终用户的软件产品**——用户直接使用界面，不写代码。
> 角色设计以**用户可感知价值**为最高判据（安装即用、启动快、失败有友好提示、隐私数据不出本地）。
> 具体做什么产品、什么领域，属用例内容（见 `product/`），不进本层；API/绑定协议等只是实现手段，不是产品本身。

---

## 0. 设计原则

1. **先角色，后 agent**：先定职责分工，再为每个角色写可执行 agent 文件。角色是"要做什么"的抽象，agent 是"怎么执行"的实现。
2. **角色正文与客户端注册分离**：`agents/<role>.md` 只写职责与交付要求；能力约束（能否写、能写哪、能否派发）写在 `manifest.json`，由生成器翻译成各客户端语法。**同一份事实源，多份生成物**，避免换客户端就失效。
3. **职责不重叠**：每个角色有明确的"专属职责 + 移交规则"，防止多个 agent 抢做同一件事或互相推诿。
4. **按工种拆分执行角色**：工具链/评审标准不同的工种必须独立设角色（见第 2 节）。
5. **可裁剪**：小项目按需裁剪启用哪些 agent，角色设计保持完整（见第 6 节）。

## 1. 角色总览（12 个）

| 7 | 质量 | `reviewer` | 代码质量审查 | 只读 |
| 8 | 质量 | `test-engineer` | 单测 + 用户场景 E2E | 写 tests/ |
| 9 | 质量 | `security-reviewer` | 安全 + 用户数据隐私审计 | 只读 |
| 10 | 交付 | `doc-engineer` | 用户手册、应用内帮助、FAQ | 写 docs/ |

## 2. 为什么按工种拆分执行角色

本产品默认有三种技术栈，工具链与评审标准完全不同，**必须按工种设独立角色**：

| 工种 | 栈 | 构建/测试工具 | 评审重点 |
|------|-----|--------------|---------|
| C++ 核心 | C++11 | CMake / GTest | 跨平台、内存安全、C++11 合规、崩溃恢复 |
| Python | Python 3 | pytest / ruff | 类型注解、脚本稳定性、依赖锁定（内部工具链） |
| 前端 | 原生静态页（HTML/CSS/JS） | 无构建、无 Node 依赖；测试由 `test-engineer` 的 E2E 把关 | 可访问性、交互一致性、错误状态覆盖（产品主界面） |

> 各工种的产物目录均在 `product/` 下（`src/`、`python/`、`web/`）。是否启用某工种由用例决定（如纯前端需求可裁剪 `cpp-implementer`）。

**判断标准**：当工种的**工具链、评审标准、产出物目录**三者都不同时拆分；同工种内不按阶段再拆（避免角色爆炸）。审查角色不按工种拆文件，而是**一个 `reviewer` + 分工种审查清单**（见第 4.7 节）。

## 3. 各角色详述

> 所有角色的**完成标准都包含**「按 `agents.md` §6.6 写审计文档到 `product/docs/audit/`」——这是门禁放行的凭证。下列各角色的完成标准只列**角色特有**的部分。

### 3.1 `product-manager`（规划）
- **职责**：用户研究与需求管理，产出 PRD（`product/docs/prd/`）、用户故事、里程碑与优先级。一切需求以**用户场景**表达（如"用户打开后 2 秒内可用"），禁止以 API 能力表达。
- **输入**：用户反馈、使用数据、业务目标。
- **输出**：`product/docs/prd/PRD-<feature>.md`（用户故事 + 可用性验收标准）、`product/docs/prd/ROADMAP.md`。
- **移交**：向 `architect` 提供用户故事 + 非功能需求（启动时间、响应延迟、资源上限、支持平台矩阵、隐私红线）。
- **完成标准**：每条需求有 Given/When/Then 验收标准；无"尽快""更好"等模糊表述；非功能需求均可被用户感知。

### 3.2 `architect`（规划）
- **职责**：应用架构、模块划分、**模块间接口契约**、技术选型、ADR、**隐私架构**（用户数据处理路径必须本地闭环）。
- **输入**：PRD（用户故事）。
- **输出**：`product/docs/design/<feature>.md`、`product/docs/adr/`、**各工种接口契约**（核心模块头文件 / 内部工具脚本协议 / 前端 ↔ 核心通信协议）。
- **约束**：C++ 侧设计必须满足跨平台要求（编译期宏隔离平台差异）；**用户数据默认不出本地**，遥测/崩溃上报须显式开关且脱敏；公开接口变更为 breaking change。
- **完成标准**：各工种的实现者可依据契约并行开工，无需追问。

### 3.3 `cpp-implementer`（执行 / C++ 工种）
- **职责**：实现 `product/src/`、`product/include/` 下的 C++11 代码及对应单测。核心模块（用例定义）：核心业务逻辑、平台系统能力、文件与资源管理。
- **输入**：模块契约（architect 产出）。
- **输出**：可编译实现 + GTest 用例。
- **硬约束**：仅用 C++11（禁 C++14+）；平台差异隔离为 `*_win32/posix/apple.cpp` 并同步 `CMakeLists.txt` 的 `target_sources` 分支；路径用 `/`；对外 UTF-8；头文件无 `using namespace`；**任何失败须给上层可呈现给用户的错误信息，不得崩溃或静默失败**。
- **完成标准**：至少一个平台构建无新增 warning；相关 `ctest` 通过。

### 3.4 `python-implementer`（执行 / Python 工种）
- **职责**：`product/python/` 下的**内部工具链**——转换/处理/评测脚本、打包辅助脚本（用例定义具体内容）。用户不可见，不随产品安装包分发。
- **输入**：工具需求（`architect`/`release-engineer` 提出）。
- **输出**：脚本 + pytest 用例。
- **硬约束**：脚本必须有类型注解；依赖固定版本并写入 lock 文件；输出确定性（固定随机种子）。
- **完成标准**：pytest 全绿；工具产物经 `test-engineer` 验证可用。

### 3.5 `frontend-implementer`（执行 / 前端工种，核心）
- **职责**：实现 `web/` 下的**产品主界面**（用户直接使用，非演示）。形态为**原生静态页**（`index.html` + `app.js` + `styles.css`），**免构建、零 Node 依赖**——产品需离线可用且安装即用，引入打包链会带来网络依赖与构建门禁成本（理由由 `architect` 在用例契约中记录）。含首启体验、空状态、错误恢复、离线可用。
- **输入**：界面稿（ui-designer）+ 通信协议（architect）。
- **输出**：`web/` 静态资源（产品本体）。
- **硬约束**：遵循 `design/` 设计系统，不内联硬编码样式；通信走 architect 定义的协议端点，不自造接口；**交互失败须给用户可理解的提示，不暴露堆栈/技术细节**。
- **测试边界**：免构建形态下无 JS 单测层，前端质量由 `test-engineer` 的**用户场景 E2E** 把关（首启/空数据/断网，不 mock 核心链路）。
- **完成标准**：静态资源经服务正确返回（200 + 匹配的 Content-Type + UTF-8）；零 CDN、零运行时外部请求；用户场景冒烟通过（首启/空数据/断网不白屏）。若日后界面复杂度显著上升而引入构建工具，须保持相对路径（`base: './'`）与零 CDN 约束。

### 3.6 `ui-designer`（执行 / 设计工种，核心）
- **职责**：`design/` 下的设计系统（色彩/字体/间距/组件规范，含默认/hover/disabled/error/empty 状态）、交互流程、界面稿。**必含首启引导、空状态、错误态、离线态**。
- **输入**：PRD 用户故事。
- **输出**：设计系统文档 + 界面稿（标注尺寸/状态，交付 `frontend-implementer`）。
- **约束**：核心角色（界面即产品本体），不可裁剪；设计资产版本化管理。
- **完成标准**：组件规范覆盖全部界面与异常态；`frontend-implementer` 可无追问还原界面。

### 3.7 `reviewer`（质量 / 通用 + 工种清单）
- **职责**：代码审查。**通用审查协议 + 分工种清单**：
  - C++ 清单：C++11 合规、跨平台宏隔离、内存安全（RAII）、统一导出宏（如 `<LIB>_API`）、测试配套。
  - Python 清单：类型注解、依赖锁定、错误处理、绑定一致性。
  - 前端清单：可访问性、组件复用、包体积、XSS 防护。
- **只读**：不直接改代码，输出修改建议交对应工种实现者。
- **输出格式**：分级 🔴阻塞/🟡建议/🟢可选；每条给 `文件:行号` + 问题 + 依据条款 + 建议。
- **完成标准**：结论二选一 `✅ 通过` / `❌ 需修改`；阻塞项清零才 ✅。

### 3.8 `test-engineer`（质量）
- **职责**：测试策略、`tests/` 用例、bug 复现测试、跨平台测试矩阵、**用户场景 E2E**（从安装包/可执行启动走真实用户路径，不 mock 核心链路；含首启、空数据、断网）。
- **流程**：先写能复现 bug 的失败测试 → 交对应工种实现者修复 → 确认转绿。
- **输入**：各工种实现产物。
- **输出**：测试套件 + 测试报告。
- **完成标准**：全量用例绿；用户主路径 E2E 通过；平台相关逻辑三平台验证。

### 3.9 `security-reviewer`（质量）
- **职责**：安全与**隐私**审计——隐私红线（用户数据不上传、不落明文日志、遥测显式开关且脱敏）、输入校验、依赖 CVE、并发安全、前端 XSS。
- **只读**。
- **输出格式**：风险分级 Critical/High/Medium/Low + CWE 编号 + 修复建议。
- **完成标准**：无 Critical/High 才放行（G3 门禁）。

### 3.10 `doc-engineer`（交付）
- **职责**：**面向用户的文档**——README（产品能解决什么问题、如何安装、如何出第一个结果）、用户手册（`product/docs/manual/`）、应用内帮助文案、FAQ、CHANGELOG（用户视角描述变化）。
- **硬约束**：不用开发者行话（API/SDK/ABI）；步骤与实际 UI 一致（`frontend-implementer` 变更须同步）；内部开发者文档（构建/架构）归 `architect`。
- **完成标准**：一个从没接触过产品的用户能按文档完成安装到出结果的全流程。

### 3.11 `release-engineer`（交付）
- **职责**：语义化版本、**三平台安装包**（Windows: MSI/NSIS；macOS: 签名 dmg/pkg + 公证；Linux: deb/AppImage）、**代码签名与公证**、**自动更新通道**、CI/CD 矩阵、发布检查单。
- **输入**：各角色交付物。
- **输出**：版本 tag、安装包与签名、更新清单与校验和、CI 配置。
- **约束**：发布前必须过 G3 门禁；Python 内部工具链不进安装包；构建产物不入库。
- **完成标准**：三平台安装包冒烟通过（安装→首启→出结果）；签名有效、更新通道可用；检查单全绿。

### 3.12 `orchestrator`（协调）
- **职责**：拆解任务、按角色/工种分配、跟踪进度、收敛产出。
- **派发前校验 G1**：向 `architect` / `ui-designer` / 任何实现角色派发任务前，先确认 `product/docs/prd/` 存在覆盖本次范围的 PRD，且每条需求带 Given/When/Then 验收标准。缺失则**先派 `product-manager`**，不得跳过规划阶段直接派实现 —— `architect` 与 `ui-designer` 均声明 PRD 为输入，无 PRD 开工会导致需求无源、验收无基准、用户场景无可回溯依据。
- **原则**：G1→G4 门禁按序放行；并行实现时不同工种改不同目录，避免冲突。
- **完成标准**：全部子任务完成且门禁通过，产出收敛交付。

## 4. 协作流水线与门禁

```text
PRD(用户故事) → 设计+契约(architect) + 界面稿(ui-designer)
  → 并行实现：cpp-implementer ∥ python-implementer(内部工具) ∥ frontend-implementer
  → 审查(reviewer) → 测试(单测 + 用户场景E2E) → 安全+隐私(security-reviewer)
  → 用户文档(doc-engineer) → 安装包+签名+更新(release-engineer)
全程 orchestrator 协调。
```

| 门禁 | 位置 | 放行条件 |
|------|------|---------|
| G1 设计 | 设计→实现 | `product-manager` 的 PRD 已存在且含 Given/When/Then 验收标准 + architect 模块契约 + ui-designer 界面稿（含空状态/错误态）；三者各有审计文档 |
| G2 合入 | 实现→测试 | `reviewer` ✅（按对应工种清单）+ 对应实现角色有审计文档 |
| G3 质量 | 测试→交付 | `test-engineer` 单测 + 用户场景 E2E 全绿 + `security-reviewer` 无 Critical/High；两者各有审计文档 |
| G4 发布 | 文档→发布 | `doc-engineer` 用户文档完成 + `release-engineer` 签名/安装包/更新通道检查单全绿；两者各有审计文档 |

> 每道门禁要求对应角色已在 `product/docs/audit/` 留痕（规范见 `agents.md` §6.6）——审计文档是该环节确已发生的凭证，`orchestrator` 放行前核验。

## 5. 角色 → Agent 映射规则

| 项 | 规则 |
|----|------|
| 文件位置 | 一个角色 = `agents/<role-name>.md`（本目录下，**纯职责正文，无 frontmatter**） |
| 能力声明 | `manifest.json`：`capability`（`read-only`/`read-write`/`dispatch`）+ `paths` 白名单 + `may_dispatch` |
| 注册文件 | 由 `scripts/gen_agents.py` 生成 `.opencode/agents/<id>.md` 与 `.claude/agents/<id>.md`，**勿手改** |
| 工具权限 | 只读角色禁止 edit（仅允许写审计）；写角色只在 `paths` 内可写 |
| 实例化 | 按 `invocation.md`：`dispatch` → `await` → `collect`；无子代理时人工串行 |
| 优先级 | 角色文件 → 本全局约束 → 运行时 rolePrompt → 具体任务指令（高层覆盖同名冲突字段） |
| 活文档 | 验证有效的改进回写角色文件、`manifest.json` 与本文档，再重新生成 |

## 6. 裁剪原则

1. **MVP 阶段**：可后置 `python-implementer`（先用现成工具/手动脚本）、可先单平台交付；`ui-designer`/`frontend-implementer` **不裁**——用户产品的界面即本体；`security-reviewer` **不裁**——隐私债越晚还越贵。
2. **单人模式**：`orchestrator` 由人类承担；其余角色按任务逐个动态实例化（一个会话可先后扮演多角色，但结论格式不变）。
3. **审查合并**：小项目 `reviewer` 与 `test-engineer` 可由同一会话先后执行，但结论格式不变。
4. 裁剪决策记入 `product/docs/adr/`，保持可追溯。
