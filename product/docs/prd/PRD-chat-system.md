## 1. 背景与问题

用户现有产品 `aimodel` 的核心骨架是一套**本地 HTTP 服务 + 本地浏览器界面**的「系统信息报告」工具：用户启动 `system_info_ui` 后，页面在 `127.0.0.1` 上显示硬件报告（CPU/GPU/内存/磁盘/打印机）。

但这种「仪表盘 + 局域网服务器」的形态，**缺少一个面向用户的对话入口**。当前产品没有「对话式交互」：
- 用户不能直接用自然语言问“我这台电脑能不能跑一个 7B 的模型？”
- 用户不能让系统帮他“根据显存和内存自动推荐一个合适的模型大小”；
- 若要回答这类问题，只能手动解析 CPU/显卡/内存/硬盘字段，工作量大。

因此，为产品补上一层**对话/聊天系统**，是从“报告一次性展示”走向“对话式交互”的自然一步，也是后续更强大 AI 能力（模型选择、任务规划）落地的地基。

---

## 2. 目标（用户可感知）

| # | 目标 | 衡量方式 |
|---|------|---------|
| G1 | 用户能用自然语言提出一个“我的电脑能做什么、应该用什么模型”问题，产品给出有用、可信的回答 | 界面可用；回答可理解 |
| G2 | 产品能基于用户的本机信息（CPU/显卡/内存/硬盘/架构）给出**具体建议**，不只复读一个模板 | 回答中出现用户的实际配置 |
| G3 | 产品能给出**可执行的下一步**（例如“可用此序列安装 4-bit 量化模型”） | 回答中有明确动作 |
| G4 | 答案可信、可解释：给出所依据的配置与限制 | 回答含配置摘要与边界说明 |
| G5 | 隐私合规：默认只在本机，**不向外传输用户数据** | 浏览器网络面板显示仅本地连接 |
| G6 | 界面维持当前产品的“硬件报告”页面，不强行改成对话机器人 | 现有页面结构、卡片顺序不变 |

## 3. 范围

### 3.1 本期交付（Must）

作为一个**对话入口**，不做完整的 AI 推理引擎。产品在用户提出一句话需求后，通过已有“硬件报告”能力做一次**推荐/建议**。建议中必须包含两个部分：

1. **配置摘要**：基于用户本机的 CPU/显卡/内存/硬盘概览；
2. **可执行建议**：给出“能跑 / 需检查 / 不建议”分类，并给出可操作步骤。

用例的具体数据（CPU、显卡、显存、内存、硬盘）全部来自 `product/src/cpp/` 采集的系统信息 API（与硬件报告共用同一份数据）；聊天内容只作为前端交互，不改现有硬件报告的 UI 结构。

### 3.2 可选延伸（可做，不做不影响本期）

- 更完整的多轮对话记忆；
- 内置 AI 模型选择与量化推荐的完整逻辑（这一部分有一套 API/数据平面，需要 `architect` 再出契约）；
- 文本问答功能覆盖不在本期范围内（仅以“推荐/下一步”为目标）；
- 离线优先的多轮会话管理。

### 3.3 已有系统与通信原则

本 PRD 建立在已存在的系统能力上，并假设产品的**对话接入点与现有本地服务一致**：

- 现有 `product/tools/system_info_ui.cpp` 已作为产品入口：启动后打开本地浏览器，默认绑定 `127.0.0.1`；
- 现有 `product/src/cpp/` 定义了系统信息 API，`http_server` 负责路由与静态资源服务；
- 当前界面为 **无构建原生静态页**（`product/web/`），`build.ps1` 复制 `web/` 到可执行文件同级目录。

因此，聊天系统在本期的实现策略为：**把自然语言交互作为产品入口的一部分，复用已有数据与路由边界**；它的用户接口形态因此不会是“另一个页面”，而是“同一界面里增加一个对话/推荐模块”。

### 3.4 显式排除

- 不开放外部网络 API 为本期目标；
- 不要求跨设备同步聊天记录；
- 不要求用大模型驱动聊天机器人（该项留给 v0.2+，见 `ROADMAP.md`）。

## 4. 用户故事（Given/When/Then）

### US-1 查看我的电脑能做什么
**用户**：普通用户，想知道自己的电脑能跑多大模型。  
**场景**：用户打开产品后，看到一个“聊天/对话”入口。  
**Given**：产品已启动，用户可见界面为“硬件报告”卡片页。  
**When**：用户在界面上点“对话/推荐”并提出“我这电脑能不能跑 7B 模型”后按发送/回车。  
**Then**：产品返回一个“你的电脑能跑大概什么级别”的回答，并附上简短可执行步骤。

### US-2 回答包含用户实际配置
**用户**：普通用户，想确信产品不是泛泛而谈。  
**Scenario**：用户提问后，产品显示一段“你本机配置摘要”。  
**Given**：用户已在界面提出某项问。  
**When**：产品回答的正文返回。  
**Then**：该回答中至少含用户本机 CPU/显卡/显存/内存与硬盘的一个摘要，方便用户核对。

### US-3 给出可执行下一步
**用户**：用户要知道「下一步我该干什么」。  
**Scenario**：用户在界面上提出需求后。  
**When**：产品返回建议。  
**Then**：建议中明确给出“可用/需检查/不建议”分类，并尽量给出具体步骤（例如安装命令、模型大小推荐）；若无法确定某项，可给“先检查”的动作。

### US-4 重要限制要被坦诚告知
**用户**：用户不希望被错误的“能跑”判断误导。  
**Scenario**：用户问“我能跑多大模型”。  
**When**：产品给出推荐。  
**Then**：产品明确回答：**“这是基于你当前硬件报告的粗略推荐，未调用外部模型；如需精确判断，请你按下列步骤核对”**；并说明哪些前提假设影响结论。

### US-5 隐私合规
**用户**：用户要求产品不把数据发出去。  
**Scenario**：用户提交问题。  
**Then**：产品只在 `127.0.0.1` 本地交互；浏览器网络面板显示仅本地连接；未收集用户个人信息。无需用户提前打开某个专门开关。

### US-6 界面不被破坏
**用户**：用户不希望新功能打乱已有页面。  
**Scenario**：产品已有“硬件报告”页面。  
**Then**：引入对话/推荐模块后，现有硬件报告卡片顺序、布局、刷新/重试、隐私标识不变；新增部分仅作为增量交互。

## 5. 验收标准（按用户故事编号）

| ID | 验收点 | 测量方式 |
|----|--------|----------|
| US-1 | 产品能用自然语言接收问题并返回建议 | 页面含问答入口并能返回建议 |
| US-2 | 答案含用户实际配置摘要 | 截取答案包含 CPU/显卡/显存/内存/硬盘信息 |
| US-3 | 答案含“可用/需检查/不建议”与下一步建议 | 答案按该分类给出 |
| US-4 | 明确告知不确定性与前提假设 | 答案含“粗略推荐/未调用外部模型/按下列步骤核对”等表述 |
| US-5 | 隐私合规 | 浏览器网络面板仅 127.0.0.1；无上传客户信息 |
| US-6 | 界面不被破坏 | 无新增页面/入口、无重排现有卡片 |
| US-7 | 产品生命周期可验证 | 需求进入 ROADMAP 并随后形成用例/测试 |

## 6. 非功能需求（NFR）

### NFR-1 启动与交互
| 项 | 要求 |
|----|------|
| 首屏显示 | 给用户可感知的界面不应因新功能显著变慢 |
| 回答延迟 | 单次推荐题平均应在**3 秒内**给出初步结果（本地建议计算，不含外部模型） |
| 界面可见性 | 对话/推荐入口应在几次点击内可见 |

> 注：若本期只交付“推荐/建议”的本机计算，实际“响应延迟”通常会显著低于上述数字；上述数字仅作为硬性门槛。若实际低于要求时，应在发布检查单上写明。

### NFR-2 资源与平台
| 项 | 要求 |
|----|------|
| 内存占用 | 非产品服务进程工作集应与现有 `system_info_ui.exe` 类似（本仓库实测为 **6.8 MB 左右**工作集） |
| 平台 | 仅在 `product/` 内实现，**不承诺跨平台**；Windows 平台通过 `product/scripts/build.ps1` 已验证 |

> 注：`product/` 现有构建已覆盖 Win32（`system_info_ui.vcxproj` 含 `Win32` 与 `Release` 配置），不支持 Linux/macOS。

### NFR-3 隐私与安全
| 项 | 要求 |
|----|------|
| 数据出境 | 默认 **0 客户数据外发** |
| 日志 | 本地建议/推荐过程中不产生可追踪到用户个人身份的数据 |
| 输入 | 用户输入仅用于本地推荐计算，不落盘、不打日志 |
| 验证方式 | 浏览器网络面板观察本地连接；手工查询时确认无外部 API 调用 |

NFR-3 的验证依赖一个**局域网/本地隔离环境**：如果生产机本身联网，建议用开发盒或虚拟机测，但**不应在生产机上做「外发随机测试」**。

### NFR-4 回归保护
| 项 | 要求 |
|----|------|
| 现有功能不回归 | 重复跑现有硬件报告路径后，确认页面、卡片、查询/刷新及隐私标识仍正常 |
| 构建 | 新增代码应加入项目构建与测试流程 |
| 代码风格 | 遵循 `product/CMakeLists.txt`、`product/scripts/build.ps1` 的现有约定 |
