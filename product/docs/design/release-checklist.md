### 6.2 根因与处置

**根因不是校验和，是响应体。**

初版 `/api/save/open` 返回**全量存档**（契约 §4 初稿的 `{"ok":true,"save":{...}}`，
`...` 含全部槽位）。实测发现：

- `SaveToJson` 在全仓库**只有一个调用点**——HTTP 的 open 响应；
- CLI 根本不用 JSON，只出文本报告；
- 前端从 open 响应里**只读两个字段**：`save.version` 与 `save.diagnostics`。

也就是说 99 MB 存档下，那次序列化产出约 500 MB JSON，其中 99.99% 没有任何消费者。
唯一的「用户」是一条 E2E 断言。

**处置（已执行）**：

| 步骤 | 内容 |
|------|------|
| 契约 | §4 修订：`open` 只回 `version` / `created` / `slot_count` / `diagnostics`；槽位概要走 `/api/save/slots`，详情走 `/api/save/slot?index=<n>` |
| 核心 | 新增 `SaveMetaToJson`；`SaveToJson` 保留在公开 API（库使用者可能需要全量快照）但 HTTP 层不再调用 |
| 测试 | E2E 断言 `open` 响应**不含** `slots`，防止有人为迁就断言把全量塞回去 |
| 测试 | 新增 JSON **结构**校验（此前 JSON 断言全是子串查找，挡不住漏引号这类错误） |

**顺带发现的一个真实问题**：改完后 C++ 41/41 **依然全绿**，而 `SaveMetaToJson`
漏掉了 `created` 值的结束引号，产出非法 JSON——是 E2E 炸出来的。
原因见 §6.3。

### 6.3 测试断言强度不足（已在同轮修复）

| 项 | 内容 |
|----|------|
| 现象 | 此前所有 JSON 断言都是 `EXPECT_NE(json.find("\"level\":11"), npos)` 这类**子串查找** |
| 为什么不够 | 子串断言只证明「某段文本出现过」，不能证明「它是一份合法 JSON」。漏一个引号，所有子串照样命中 |
| 修复 | 新增 `JsonScanner`——按 JSON 语法逐字符校验字符串闭合、逗号冒号位置、转义合法性、尾部无垃圾 |
| 验证方式 | **变异测试**：故意把引号改回去 → `JsonSerializersProduceWellFormedJson` 由绿转红；改回 → 恢复绿 |

> 没有做变异验证的话，很难说清新测试是真有效还是只是「看起来在测」。

### 6.4 仍存在的限制：内存

打开 99 MB 存档后进程常驻约 **420 MB**（约文件大小的 4 倍）。
主因是 `Item` 每个实例都存一个 `std::string name`，而实际只有少数几个不同名字。

**未处置**，因为修它要改 `Item` 的结构定义，而那属于 G1 冻结的契约 §3.2，
应作为独立议题走 ADR（见 §6.2 处置表中的选项 C）。

按 512 MB 工具上限外推，内存约 2 GB——**时间维度已达标，内存维度仍是已知限制**。

### 7.1 签名与放行的建议（本轮新增）

**建议：不为 0.1.0 采购代码签名证书，按「未签名的试用分发」发布 Windows 版。**

理由：

| # | 依据 |
|---|------|
| 1 | 签名证书是**持续的年度费用**，而 0.1.0 的目标用户是愿意点「仍要打开」的小范围使用者。买证书解决的是「信任」，但当前阶段缺的是「功能验证」 |
| 2 | README 与 FAQ 已说明首次运行会提示「来自身份不明的开发者」及处理方式（§3.5），不会造成无法使用的阻塞 |
| 3 | **先验证 macOS/Linux 能否编译，再投签名成本**才是正确顺序。本轮已按 §7 把这两项延期，但这不等于它们已验证——顺序反了会浪费证书钱 |
| 4 | 签名的真实收益要到有分发渠道时才兑现。现在没有自动更新通道（§3.4），签名并不能阻止「拿不到新版」的问题 |

**该建议的代价，如实记录**：Windows SmartScreen 可能对未签名程序显示更严厉的警告，
首次运行需要用户主动绕过。对试用分发可接受，对公开分发不可接受。

若将来决定公开分发，解阻条件为：采购 OV/EV 证书 → 在 CI 配置 `signtool` 与凭据
→ 复跑本检查单 §2/§4 → 重走 G4。

#### 无签名下的最低保障

既然不做签名，至少要让用户能自查文件是否被篡改：

| # | 措施 | 状态 |
|---|------|------|
| 1 | 提供 SHA256 校验值，并在分发说明中给出核对方法 | ✅ |
| 2 | 明确写出**校验值不能替代签名**——它只证明「与发布时一致」，不证明「安全」 | ✅ |
| 3 | 建议试用者选用 ZIP 免安装形态（不留注册表、删目录即回退） | ✅ |
| 4 | 写明安全顾虑时的处置建议：**校验值一致可按误报加白名单；不一致则删除** | ✅ |
| 5 | 索取反馈时要求先提供校验值，并劝阻用户附上存档文件本身 | ✅ |

> 第 2 条尤其重要。把 SHA256 说成「安全验证」是误导——
> 它防的是「传输过程被替换」，防不了「发布者本身不可信」。

#### 回退方案

发放前须确认：任一渠道的分发件可随时撤回，撤回路径为删除发布资源。
因本产品无自动更新通道（§3.4），撤回不影响已下载的本地副本——
**这是无签名 + 无更新通道组合的真实风险，此处如实记录**。

即使采纳「未签名试用分发」，G4 **仍然不通过**——
因为 `roles.md` §3.11 的完成标准明确要求「签名有效、更新通道可用」。

这不是工程问题，是**框架与现实脱节**：`roles.md` §3.8 的完成标准
与 §4 的门禁条件本身存在口径不一致（已登记为相邻缺口，见 `ADR-0001` §3）。
在本项目全程遵守「`.role-system/` 零改动」约束的前提下，
该不一致只能登记、不能自行修改。

工程侧能做的已做完。剩下的都属于外部依赖或框架决策。
