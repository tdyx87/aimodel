## 2. 内存架构（本契约的核心）

### 2.1 分层预算

所有层共用一个预算池，**层层封顶**。下层超限直接导致上层不可达，
因此每层都必须自己先拒绝，而不是等总爆掉。

| 层 | 预算 | 触顶行为 |
|----|------|----------|
| 传输层单帧缓冲 | 64 KB | 单帧超限即报错断开（协议帧不应更大） |
| 解析器瞬时 arena | 2 MB | 超限即中止当前响应 |
| 工具结果单次上限 | 1 MB | 超限即**截断**并显式标注（不是丢弃） |
| 会话历史窗口 | 4 MB | 超限按**最旧完整轮次**淘汰，并在 UI 明示丢弃量 |
| 文件读入 | 4 MB | 超限即截断 + 行号标注 + 显式告知 |
| 进程 RSS 硬上限 | 32 MB | 触及即中止操作并报错（PRD NFR-1） |

### 2.2 硬性设计约束（违反即视为违约，不接受「实现时再说」）

| # | 约束 | 为什么必须是硬约束 |
|---|------|------------------|
| C1 | **传输层不得提供「读全量响应」的接口** | 只要存在这种接口，实现就会走捷径；一旦被调用，内存立即失控。**让犯错在 API 层不可能** |
| C2 | 所有流式处理必须走增量回调 | 整块缓冲 = 峰值内存 = 响应大小 |
| C3 | 禁止无上限的 `realloc`/`malloc` 循环增长 | 解析大 JSON 时的经典 OOM 来源 |
| C4 | 工具结果进入对话前必须经过截断器 | 否则一次 `cat 大文件` 就吃掉整个预算 |
| C5 | 会话历史必须按字节封顶 | 无界增长是本产品最可能的 NFR-1 破口（PRD 风险 1） |
| C6 | 禁止引入第三方 JSON 库 | 第三方解析器通常自带递归深度与 arena，内存不可预测 |
| C7 | 依赖清单固定为 libcurl，其余自研 | 依赖越少越可预测；每多一个就多一份不可控内存 |

### 2.3 分配策略

| 用途 | 策略 |
|------|------|
| 请求生命周期内的临时对象 | **arena 分配器**，整体释放，不逐个 free |
| 流式读取 | 定长环形缓冲，不扩容 |
| 配置、会话元数据 | 定长结构体 + 定长字符串字段（编译期上限） |
| 大文本（历史、工具结果） | 分段链表，固定块大小，便于按块淘汰 |

> 「定长 + 编译期上限」在本产品里不是偷懒，而是**让内存占用可预测**的手段。
> 动态内存不是不能有，是不能**不可预测**。

### 2.4 内存计量接口

```c
/* 进程 RSS（字节）。取自操作系统，不是库自己的估算。 */
int64_t ca_rss_bytes(void);
/* 峰值 RSS（字节）。 */
int64_t ca_peak_rss_bytes(void);
```

- Windows：`GetProcessMemoryInfo`
- POSIX：`/proc/self/statm`，无 `/proc` 时回退 `getrusage`

**约束**：该接口的返回值必须能由第三方独立复核。内置内存命令（US-7）
与第三方验收脚本（A1）必须调用同一实现但**互不引用**。

### 2.5 实测数据（2026-10-15）

#### 2.5.1 分帧与传输链路的内存（契约 T2）

`sse_test` 与 `http_test` 的实测输出：

| 项 | 分帧层 `sse_test` | 端到端 `http_test` |
|----|------------------|-------------------|
| 数据量 | **100 MB** | **100 MB** |
| 帧数 | **11,650,844** | **4,993,219** |
| 分帧器最大残片 | **4 字节** | **0 字节** |
| 进程 RSS 增量 | **0.09 MB** | **0.02 MB** |
| 耗时 | 3.57 秒 | — |

结论：**C1「不得整块缓冲」在分帧层与传输链路均已有可测证据。**
100 MB 响应对应的 RSS 增量分别是 0.09 MB 与 0.02 MB —— 差三个数量级。
若将来有人在解析里偷偷整块缓冲，本用例会先红。

测试自身**不**预分配 100 MB —— 否则测试的内存会掩盖被测代码的内存。

### 2.5.2 性能：曾为 O(n²)

第一版分帧器在密集小帧下耗时 **242 秒**（100 MB），原因是：
每消费一帧就 `memmove` 整个剩余缓冲 —— 7281 帧 × 64 KB × 1600 批
≈ **762 GB 的内存搬运**，量级上是 O(n²)。

改为**读游标 + 扫描游标**（只挪游标，不每帧搬运；游标过半才压回起点）后：

| | 修复前 | 修复后 |
|---|--------|--------|
| 100 MB 密集帧耗时 | 242 秒 | **3.57 秒** |
| 内存 | — | 不变（RSS 增量 0.09 MB） |

> 内存正确但速度不可用的流式解析，等于没做。这个缺陷是靠**看测试耗时**
> 发现的 —— 断言全绿、功能全对，只有耗时从 2 秒涨到 242 秒暴露了它。
> 因此测试耗时应与测试结果同等对待。

### 2.5.3 当前进程基线

NFR-1 承诺的是**空闲常驻** RSS。单元测试跑完即退出，测不出那个数字 ——
而那才是用户真正感受到的成本（终端里开着不关的代理，每天吃掉多少 RAM）。
因此加了 `mem_probe`：初始化各层后静默待命，供外部采样。

**实测结果**：

| 测量方式 | 结果 |
|----------|------|
| 产品内部自测（`mem_test`） | 5.14 MB |
| **独立脚本复核**（`scripts/verify_memory.py`，8 MB 预算） | **5.43 MB，余量 2.57 MB** |

逐层增量的实测（每加一层就用同一脚本复测）：

| 层 | 累计 RSS | 该层增量 |
|----|----------|----------|
| mem + buf + sse | 5.14 MB | — |
| + json | 5.23 MB | **+0.09 MB**（零分配设计） |
| + llm | 5.43 MB | **+0.20 MB**（8×32 KB 定长工具槽位） |

> llm 层的增量与设计值吻合：`8 槽位 × 32 KB = 256 KB`。
> 这是**常驻开销**而非按需分配，所以必须计入基线——
> 把常驻内存当成「用的时候才花」，正是这类工具内存失控的起点。

> 独立复核**完全不使用 cagent 的任何代码**，只用操作系统接口读 RSS
> （Windows: psapi 的 `GetProcessMemoryInfo`；POSIX: `/proc/<pid>/statm`）。
> 理由：产品内置的内存查询服务于**用户**（我想知道我用了多少），
> 验收脚本服务于**门禁**（你承诺了多少）。两者若是同一份代码，就是自己给自己打分。
> 这一点直接对应 PRD §7 的 A1。

**范围声明**：该数字覆盖 mem + buf + sse + json + llm + http(内存后端) 六层。
**尚未包含 tools / session / ui**，故 NFR-1 仍**未确认达成**。

### 2.5.4 传输后端的可用性状态（如实记录）

| 后端 | 状态 |
|------|------|
| 内存后端 | ✅ 已实现并测试（23 次检查 0 失败） |
| libcurl 后端 | ⚠️ **本机未编译验证** |

本机（Windows / MSVC）只有 `curl.exe`，**没有开发文件**；
`find_package(CURL)` 为 NOTFOUND。curl.se 只提供 MinGW 包，
无 MSVC 导入库，因此本地无法链接。

处理方式：

| 决策 | 理由 |
|------|------|
| 传输做成 `ca_transport_ops` 接口 | 契约 C1 要求「只有流式回调」，做成接口等于**结构上强制**，而不是靠注释提醒 |
| libcurl 缺失时**降级而非报错** | 其余层仍可构建与测试。NSIS 那次的教训：把可选依赖设为硬前置，一次包源抖动就拖红整条 CI 腿 |
| libcurl 实现由 CI 验证 | GitHub 运行器三平台均自带 libcurl 开发包 |

**诚实声明**：`src/transport_curl.c` 目前**未经编译验证**，
其首次编译将在 CI 上发生。若编译失败，问题会立刻暴露（编译错误而非静默降级），
但在此之前不得声称该后端可用。

### 2.5.3 实现期发现并修正的三处

| # | 问题 | 性质 |
|---|------|------|
| 1 | `find_frame_end` 只匹配相邻 `\n\n`，CRLF 流（`\n\r\n`）一帧都解析不出 | 实现缺陷。契约 §4.2 明确要求容忍 CRLF，用例已覆盖 |
| 2 | 多 `data:` 行就地压缩时，压缩区**覆盖了 event/id 的值** | 实现缺陷。表现为 data 正确、event 变空串。改为写入**独立定长缓冲**，总量仍是常数 |
| 3 | 测试自身越界写（缓冲按 chunk 精确分配，却写入 `payload[chunk]`） | 测试缺陷。表现为堆损坏 `0xc0000374` 而非干净的断言失败 —— 这类失败模式比断言失败难查得多 |

> 第 2 条的教训值得单列：**in-place 压缩与"指向同一块内存的其它字段指针"天然冲突**。
> 这类 bug 不表现为崩溃、不表现为报错，而是某个字段静静地变成空值。

## 3. 模块边界

```
cagent
├─ mem      分配器与预算计量（§2）        ← 最底层，其余层依赖它
├─ buf      定长缓冲 / 环形缓冲 / 分段链表
├─ json     JSON 扫描与构造（自研，§C6）
├─ sse      SSE 分帧（§4.2）
├─ http     传输（libcurl 封装，§4.1）
├─ llm      服务适配（OpenAI 兼容 / 至少一种非兼容，§4）
├─ tools    工具实现（§5）
├─ session  会话落盘与恢复（§6）
├─ ui       终端界面（含原始模式与流式渲染，§7）
└─ core     代理主循环：组装请求 → 解析响应 → 执行工具 → 回灌结果
```

**依赖方向单向向下**：`core → {llm, tools, session, ui} → {http, sse, json, buf} → mem`。
不允许反向依赖，也不允许 `mem` 依赖任何上层。

## 4. LLM 服务协议

### 4.1 传输层

- 基于 libcurl，**仅使用写回调**流式接收（`CURLOPT_WRITEFUNCTION` + 自定义回调）
- 不设 `CURLOPT_WRITEDATA` 的大缓冲；不调用任何「读全量」辅助函数
- 强制 HTTP/1.1 或 HTTP/2 流式；禁用响应体缓冲选项
- 连接复用：同一 endpoint 复用连接，避免重复 TLS 握手
- 超时区分三类：**连接超时 / 首字节超时 / 整体空闲超时**（流式下总超时无意义）

### 4.2 SSE 分帧

| 项 | 规定 |
|----|------|
| 行分隔 | 仅 `\n`，容忍 `\r\n` |
| 帧边界 | 空行（`\n\n`）分隔 |
| 注释行 | 以 `:` 开头，忽略（心跳） |
| 字段 | `event:` / `data:` / `id:` / `retry:` |
| 单帧上限 | 64 KB，超限即报错断开（§2.1） |
| `[DONE]` | 显式结束标记，收到即停 |

### 4.3 服务适配

至少两种协议形态，差异**全部封在适配层**：

| 形态 | 差异点 |
|------|--------|
| OpenAI 兼容（`/v1/chat/completions`） | `choices[].delta.content`，工具调用用 `tool_calls` 增量拼接 |
| 至少一种非兼容 | 工具调用用独立 block（如 Anthropic 的 `content[]` 分型），终止原因字段不同 |

**契约要求**：`llm` 层对外暴露统一的增量事件流：

```c
typedef enum {
    CA_EV_TEXT_DELTA,     /* 一段增量文本 */
    CA_EV_TOOL_CALL_BEGIN,/* 工具调用开始（拿到 id 与名字） */
    CA_EV_TOOL_CALL_ARGS, /* 工具参数增量片段（可能分多片） */
    CA_EV_TOOL_CALL_END,  /* 参数收齐 */
    CA_EV_USAGE,          /* token 用量（如服务提供） */
    CA_EV_ERROR,          /* 服务端返回的错误 */
    CA_EV_DONE
} ca_event_kind;
```

上层**不得**知道底层是哪家协议。这条是 US-8 的实现基础。

## 5. 工具协议

### 5.1 工具清单（v0.1 完整）

| 工具 | 用途 | 默认权限 |
|------|------|----------|
| `read_file` | 读文件，按字节截断 + 行号 | 需确认（越权路径时） |
| `write_file` | 写/覆盖文件 | **需确认** |
| `edit_file` | 按精确匹配替换 | **需确认** |
| `list_dir` | 列目录 | 需确认 |
| `search` | 字面/正则搜索（ripgrep 式） | 需确认 |
| `run_shell` | 执行 shell 命令 | **需确认** |

### 5.2 权限模型（安全硬约束）

| 规则 | 内容 |
|------|------|
| P1 | **默认全部拒绝**。未经用户明确批准的调用不得执行 |
| P2 | 确认提示必须展示：工具名、完整参数、改动影响面（行数增减/受影响文件数） |
| P3 | 拒绝后必须向模型回灌结构化「已拒绝」结果，**不中断会话** |
| P4 | 路径必须规范化后落在工作区内；`..`、符号链接指向外部一律拒绝 |
| P5 | `run_shell` 必须展示**完整命令原文**，不得折叠或省略 |

> P4 的符号链接逃逸必须用真实用例覆盖——只测 `../` 不够，
> 符号链接是另一条路径，且更隐蔽。

### 5.3 工具结果进入对话的格式

```
<result path="src/a.c" lines="1-80" total="1200" truncated="true">
...
（截断处插入显式标注，说明省略了多少行、如何获取剩余部分）
</result>
```

**约束**：结果**必须**携带来源元信息（路径/行范围/是否截断）。
模型需要知道内容是否完整，否则会基于残缺数据下结论。

## 6. 会话持久化

| 项 | 规定 |
|----|------|
| 位置 | 用户配置目录下的 `sessions/<id>.json`，不写工作区 |
| 格式 | 单文件自包含，**单文件大小硬上限 4 MB**（与 §2.1 预算一致） |
| 列表 | 扫描目录，按修改时间排序；损坏文件**跳过并提示**，不得导致启动失败 |
| 恢复 | 读取时同样受 4 MB 上限约束；超出按 §2.1 的轮次淘汰规则截断 |
| 密钥 | **绝不写入**会话文件（PRD NFR-3） |

## 7. 终端界面

| 项 | 规定 |
|----|------|
| 原始模式 | 必须同时支持「原始模式不可用」的降级路径（如管道输入、CI 非 TTY） |
| 流式渲染 | 逐 token 追加，**不做全量重绘**（重绘是卡顿的主因） |
| 确认交互 | 就地渲染提示并等待输入；不得在渲染中途清屏导致用户看不到待批准内容 |
| 非 TTY | 管道/CI 场景自动降级为行式输出，不尝试原始模式 |

> 「原始模式不可用时怎么办」必须有测试覆盖——CI 跑测试时就是非 TTY，
> 这条不测就会在 CI 上炸。

## 9. 违约判定

以下任一情况视为违反本契约，G2 不得通过：

| # | 违约 |
|---|------|
| V1 | 传输层存在「读全量响应」接口 |
| V2 | 任一分层可无上限增长（无字节上限的累积容器） |
| V3 | 引入第三方 JSON 库 |
| V4 | 工具调用存在「默认放行」路径 |
| V5 | 路径逃逸未被拒绝（含符号链接） |
| V6 | 会话历史无字节上限 |
| V7 | 平台差异泄漏到 `core` / `llm` / `tools` |

## 10. 测试要求（契约级）

| # | 要求 |
|---|------|
| T1 | 每个内存预算都有对应的**边界用例**（恰好超限、远超限） |
| T2 | 传输层须有「永不整块缓冲」的测试：用超大响应流验证 RSS 增量受控 |
| T3 | 会话历史封顶须有测试：灌入超限历史后断言淘汰发生且**UI 有明示** |
| T4 | 权限拒绝路径须有测试：拒绝后断言会话**未中断**（P3） |
| T5 | 非 TTY 降级路径须有测试 |

> T2 是本契约最重要的一条测试。它直接对应 PRD 风险 3 与 4——
> 若实现里混入了整块缓冲，T2 必须先红。
