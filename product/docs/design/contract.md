## 2. 内存架构（本契约的核心）

### 2.1 分层预算

所有层共用一个预算池，**层层封顶**。下层超限直接导致上层不可达，
因此每层都必须自己先拒绝，而不是等总爆掉。

> **⚠ 2026-10-19 修订**：进程硬上限由 32 MB 放宽为 100 MB（ADR-0003）。
> 分层预算**未放宽** —— 它们约束的是「单次操作不得吃掉整个池」，
> 与池子总大小无关，且恰恰是防止无界增长的那几道闸。

| 层 | 预算 | 触顶行为 |
|----|------|----------|
| 传输层单帧缓冲 | 64 KB | 单帧超限即报错断开（协议帧不应更大） |
| 解析器瞬时 arena | 2 MB | 超限即中止当前响应 |
| 工具结果单次上限 | 1 MB | 超限即**截断**并显式标注（不是丢弃） |
| 会话历史窗口 | 4 MB | 超限按**最旧完整轮次**淘汰，并在 UI 明示丢弃量 |
| 单次请求体 | 默认 256 KB，可配 `CAGENT_CONTEXT_BYTES`（钳制 [16 KB, 4 MB]） | 超限先淘汰最旧完整轮次并重试；单轮独占仍超限则报错中止，提示 `/new` |
| 文件读入 | 4 MB | 超限即截断 + 行号标注 + 显式告知 |
| **运行时基线（libcurl + C 运行时）** | **实测 6.7 MB**（Linux）/ **9.4 MB**（CI runner） | 计入总预算，不是"预算外" |
| 进程 RSS 硬上限 | **100 MB** | 触及即中止操作并报错（PRD NFR-1） |

> **运行时基线必须计入预算。**
> 原 8 MB 预算的问题不是"定得太小"，而是**把 libcurl 的成本当成了 0**。
> 任何预算数字，都必须在**交付配置**（真实链接真实依赖）下测出来，
> 否则它就是个装饰。

> **⚠ 2026-10-21 修订（单次请求体）**：原实现把请求体硬编码为 16 KB，
> 与"历史窗口 4 MB"差 256 倍 —— 约 50 轮对话或一次稍大的工具结果后
> 每轮都失败（`请求体需要 N 字节，上限 16384`），实际不可用。
> 现改为**默认 256 KB**、环境变量可调（范围 [16 KB, 4 MB]，越界钳制并告知），
> 超限行为与历史窗口一致（淘汰最旧完整轮次 + UI 明示），
> 只有"单轮独占"才报错。二者共同遵守 V6「历史不得无界增长」。

### 2.2 硬性设计约束（违反即视为违约，不接受「实现时再说」）

| # | 约束 | 为什么必须是硬约束 |
|---|------|------------------|
| C1 | **传输层不得提供「读全量响应」的接口** | 只要存在这种接口，实现就会走捷径；一旦被调用，内存立即失控。**让犯错在 API 层不可能** |
| C2 | 所有流式处理必须走增量回调 | 整块缓冲 = 峰值内存 = 响应大小 |
| C3 | 禁止无上限的 `realloc`/`malloc` 循环增长 | 解析大 JSON 时的经典 OOM 来源 |
| C4 | 工具结果进入对话前必须经过截断器 | 否则一次 `cat 大文件` 就吃掉整个预算 |
| C5 | 会话历史必须按字节封顶 | 无界增长是本产品最可能的 NFR-1 破口（PRD 风险 1） |
| C6 | 禁止引入第三方 JSON 库 | 第三方解析器通常自带递归深度与 arena，内存不可预测 |
| C7 | 依赖清单固定为 libcurl，其余自研 | 依赖越少越可预测；每多一个就多一份不可控内存 |

### 2.3 分配策略

| 用途 | 策略 |
|------|------|
| 请求生命周期内的临时对象 | **arena 分配器**，整体释放，不逐个 free |
| 流式读取 | 定长环形缓冲，不扩容 |
| 配置、会话元数据 | 定长结构体 + 定长字符串字段（编译期上限） |
| 大文本（历史、工具结果） | 分段链表，固定块大小，便于按块淘汰 |

> 「定长 + 编译期上限」在本产品里不是偷懒，而是**让内存占用可预测**的手段。
> 动态内存不是不能有，是不能**不可预测**。

### 2.4 内存计量接口

```c
/* 进程 RSS（字节）。取自操作系统，不是库自己的估算。 */
int64_t ca_rss_bytes(void);
/* 峰值 RSS（字节）。 */
int64_t ca_peak_rss_bytes(void);
```

- Windows：`GetProcessMemoryInfo`
- POSIX：`/proc/self/statm`，无 `/proc` 时回退 `getrusage`

**约束**：该接口的返回值必须能由第三方独立复核。内置内存命令（US-7）
与第三方验收脚本（A1）必须调用同一实现但**互不引用**。

### 2.5 实测数据（2026-10-15）

#### 2.5.1 分帧与传输链路的内存（契约 T2）

`sse_test` 与 `http_test` 的实测输出：

| 项 | 分帧层 `sse_test` | 端到端 `http_test` |
|----|------------------|-------------------|
| 数据量 | **100 MB** | **100 MB** |
| 帧数 | **11,650,844** | **4,993,219** |
| 分帧器最大残片 | **4 字节** | **0 字节** |
| 进程 RSS 增量 | **0.09 MB** | **0.02 MB** |
| 耗时 | 3.57 秒 | — |

结论：**C1「不得整块缓冲」在分帧层与传输链路均已有可测证据。**
100 MB 响应对应的 RSS 增量分别是 0.09 MB 与 0.02 MB —— 差三个数量级。
若将来有人在解析里偷偷整块缓冲，本用例会先红。

测试自身**不**预分配 100 MB —— 否则测试的内存会掩盖被测代码的内存。

### 2.5.2 性能：曾为 O(n²)

第一版分帧器在密集小帧下耗时 **242 秒**（100 MB），原因是：
每消费一帧就 `memmove` 整个剩余缓冲 —— 7281 帧 × 64 KB × 1600 批
≈ **762 GB 的内存搬运**，量级上是 O(n²)。

改为**读游标 + 扫描游标**（只挪游标，不每帧搬运；游标过半才压回起点）后：

| | 修复前 | 修复后 |
|---|--------|--------|
| 100 MB 密集帧耗时 | 242 秒 | **3.57 秒** |
| 内存 | — | 不变（RSS 增量 0.09 MB） |

> 内存正确但速度不可用的流式解析，等于没做。这个缺陷是靠**看测试耗时**
> 发现的 —— 断言全绿、功能全对，只有耗时从 2 秒涨到 242 秒暴露了它。
> 因此测试耗时应与测试结果同等对待。

### 2.5.3 当前进程基线

NFR-1 承诺的是**空闲常驻** RSS。单元测试跑完即退出，测不出那个数字 ——
而那才是用户真正感受到的成本（终端里开着不关的代理，每天吃掉多少 RAM）。
因此加了 `mem_probe`：初始化各层后静默待命，供外部采样。

**实测结果**：

| 测量方式 | 结果 |
|----------|------|
| 产品内部自测（`mem_test`） | 5.14 MB |
| **独立脚本复核**（`scripts/verify_memory.py`，8 MB 预算） | **5.43 MB，余量 2.57 MB** |

逐层增量的实测（每加一层就用同一脚本复测）：

| 层 | 累计 RSS | 该层增量 |
|----|----------|----------|
| mem + buf + sse | 5.14 MB | — |
| + json | 5.23 MB | **+0.09 MB**（零分配设计） |
| + llm | 5.43 MB | **+0.20 MB**（8×32 KB 定长工具槽位） |

> llm 层的增量与设计值吻合：`8 槽位 × 32 KB = 256 KB`。
> 这是**常驻开销**而非按需分配，所以必须计入基线——
> 把常驻内存当成「用的时候才花」，正是这类工具内存失控的起点。

> 独立复核**完全不使用 cagent 的任何代码**，只用操作系统接口读 RSS
> （Windows: psapi 的 `GetProcessMemoryInfo`；POSIX: `/proc/<pid>/statm`）。
> 理由：产品内置的内存查询服务于**用户**（我想知道我用了多少），
> 验收脚本服务于**门禁**（你承诺了多少）。两者若是同一份代码，就是自己给自己打分。
> 这一点直接对应 PRD §7 的 A1。

**范围声明**：该数字覆盖 mem + buf + sse + json + llm + http(内存后端) 六层。
**尚未包含 tools / session / ui**，故 NFR-1 仍**未确认达成**。

### 2.5.4.1 edit_file 的三条「宁可拒绝」原则

这一层最容易出的不是「写错」，而是**静默破坏**：

| # | 原则 | 理由 |
|---|------|------|
| 1 | `old_string` 为空一律拒绝 | 空串匹配所有位置 |
| 2 | 出现多次且未显式 `replace_all` 时**拒绝** | 全量替换会静默破坏代码而不报错。要求模型提供含上下文的更长 old_string |
| 3 | 落盘走「临时文件 + 原子替换」（`rename` / `MoveFileEx`） | 直接覆盖写时，中途失败会留下半截文件——源文件被毁而用户毫不知情 |

以及 **P2 的时序**：`ca_tool_edit_preview()` 必须在**请求权限之前**算好影响面
（匹配处数 / 行数增减 / 字节增减），否则用户是在「不知道会改多少」的情况下批准。

执行时还会校验「实际替换处数 == preview 报告处数」，不一致就放弃写入——
宁可失败，也不能在用户不知情的情况下写入与**已批准内容不同**的结果。

### 2.5.4.2 为什么 search 不做正则

引入正则引擎意味着引入一套自己的回溯 / 灾难性匹配保护逻辑，
而那与「极低内存、行为可预测」的目标相悖。正则搜索应作为独立议题走 ADR。

**run_shell 的两条硬约束**：

| # | 约束 | 理由 |
|---|------|------|
| P5 | 命令**原文完整**展示给用户，不折叠不省略 | 折叠命令等于让用户盲批一件他没看清的事 |
| 超时 | 默认 60 秒硬超时，超时杀进程并报 `status="timeout"` | 挂死的命令会拖住整个代理；且**超时不能报成成功**——那会让模型以为命令做完了 |

### 2.5.5.1 本机如何拿到 libcurl 开发包

本机（Windows / MSVC）只有 `curl.exe`，没有头文件与导入库，
`find_package(CURL)` 原本是 NOTFOUND。走 Conan 失败：**Conan Center 返回 403**
（`center2.conan.io` 与 `center.conan.io` 均被拦），配置的两个镜像
（`iteale` DNS 解析失败、本机 Artifactory 未运行）也不可用。
本机缓存中没有任何 curl recipe。

因此改为从 GitHub 取 curl 源码自行构建（GitHub 可访问）：

```
cmake -S curl -B curl-b -G "Visual Studio 15 2017" -A x64 \
      -DCMAKE_INSTALL_PREFIX=<prefix> -DBUILD_SHARED_LIBS=OFF \
      -DCURL_USE_SCHANNEL=ON -DCURL_USE_OPENSSL=OFF -DCURL_USE_LIBPSL=OFF \
      -DCURL_DISABLE_LDAP=ON -DCURL_ZLIB=OFF -DBUILD_CURL_EXE=OFF
cmake --build curl-b --config Release
cmake --install curl-b --config Release --prefix <prefix>
cmake -S product -B build-curl -G "Visual Studio 15 2017" -A x64 \
      -DCMAKE_PREFIX_PATH=<prefix>
```

用 **Schannel** 而不是 OpenSSL：走系统证书库，不需要额外编一个 OpenSSL。

`product/conanfile.txt` 保留着，供能访问 Conan Center 的环境使用，但**本机走不通**。

**CI 上走的是 vcpkg**（windows-latest 自带），而非自建：
`vcpkg install curl:x64-windows-static-md` + `-DVCPKG_TARGET_TRIPLET=x64-windows-static-md`。
接线曾经是错的——装了 `-static-md` 却按默认 `x64-windows` 去找，
`VCPKG_INSTALLED_DIR` 又设成了带 triplet 的目录（工具链会再追加一次），
两处错位叠加导致 Windows 上 curl **从未被找到**。修正后 Windows 才第一次真实运行传输层。

CI 上这三件事现在是**硬门禁**（不再只是 warning）：
构建零告警、传输后端必须是 libcurl、真实请求冒烟必须成功。

在 Windows 上因 CMake 把非 ASCII 输出成 `?` 而**永远匹配不上**——
于是「Windows 从未验证过传输层」这件事被静默掩盖了很久。

> 「能连本地服务」比「能连某家云服务」弱，但它验证的是**我们自己的代码**；
> 云服务那一层还牵涉账号、配额与地区，不该混进同一个结论里。

- **`/list` 的 mtime 未做人类可读格式化**：只保证「新到旧」的排序，不显示时间——
  `localtime`/`strftime` 在 MSVC 上属于 C4996 告警源，而零告警是硬门禁。
- **`session_store` 的路径/目录遍历分支只在本机（Windows）与 CI（三平台）验证过**；
  不存在「在某个平台从未编译过」的分支，但 Linux/macOS 只在 CI 跑过。

### 2.5.7 实现期发现并修正的三处

| # | 问题 | 性质 |
|---|------|------|
| 1 | `find_frame_end` 只匹配相邻 `\n\n`，CRLF 流（`\n\r\n`）一帧都解析不出 | 实现缺陷。契约 §4.2 明确要求容忍 CRLF，用例已覆盖 |
| 2 | 多 `data:` 行就地压缩时，压缩区**覆盖了 event/id 的值** | 实现缺陷。表现为 data 正确、event 变空串。改为写入**独立定长缓冲**，总量仍是常数 |
| 3 | 测试自身越界写（缓冲按 chunk 精确分配，却写入 `payload[chunk]`） | 测试缺陷。表现为堆损坏 `0xc0000374` 而非干净的断言失败 —— 这类失败模式比断言失败难查得多 |

> 第 2 条的教训值得单列：**in-place 压缩与"指向同一块内存的其它字段指针"天然冲突**。
> 这类 bug 不表现为崩溃、不表现为报错，而是某个字段静静地变成空值。

## 3. 模块边界

```
cagent
├─ mem      分配器与预算计量（§2）        ← 最底层，其余层依赖它
├─ buf      定长缓冲 / 环形缓冲 / 分段链表
├─ json     JSON 扫描与构造（自研，§C6）
├─ sse      SSE 分帧（§4.2）
├─ http     传输（libcurl 封装，§4.1）
├─ llm      服务适配（OpenAI 兼容 / 至少一种非兼容，§4）
├─ tools    工具实现（§5）
├─ session  会话落盘与恢复（§6）
├─ ui       终端界面（含原始模式与流式渲染，§7）
└─ core     代理主循环：组装请求 → 解析响应 → 执行工具 → 回灌结果
```

**依赖方向单向向下**：`core → {llm, tools, session, ui} → {http, sse, json, buf} → mem`。
不允许反向依赖，也不允许 `mem` 依赖任何上层。

## 4. LLM 服务协议

### 4.1 传输层

- 基于 libcurl，**仅使用写回调**流式接收（`CURLOPT_WRITEFUNCTION` + 自定义回调）
- 不设 `CURLOPT_WRITEDATA` 的大缓冲；不调用任何「读全量」辅助函数
- 强制 HTTP/1.1 或 HTTP/2 流式；禁用响应体缓冲选项
- 连接复用：同一 endpoint 复用连接，避免重复 TLS 握手
- 超时区分三类：**连接超时 / 首字节超时 / 整体空闲超时**（流式下总超时无意义）

### 4.2 SSE 分帧

| 项 | 规定 |
|----|------|
| 行分隔 | 仅 `\n`，容忍 `\r\n` |
| 帧边界 | 空行（`\n\n`）分隔 |
| 注释行 | 以 `:` 开头，忽略（心跳） |
| 字段 | `event:` / `data:` / `id:` / `retry:` |
| 单帧上限 | 64 KB，超限即报错断开（§2.1） |
| `[DONE]` | 显式结束标记，收到即停 |

### 4.3 服务适配

至少两种协议形态，差异**全部封在适配层**：

| 形态 | 差异点 |
|------|--------|
| OpenAI 兼容（`/v1/chat/completions`） | `choices[].delta.content`，工具调用用 `tool_calls` 增量拼接 |
| 至少一种非兼容 | 工具调用用独立 block（如 Anthropic 的 `content[]` 分型），终止原因字段不同 |

**契约要求**：`llm` 层对外暴露统一的增量事件流：

```c
typedef enum {
    CA_EV_TEXT_DELTA,     /* 一段增量文本 */
    CA_EV_TOOL_CALL_BEGIN,/* 工具调用开始（拿到 id 与名字） */
    CA_EV_TOOL_CALL_ARGS, /* 工具参数增量片段（可能分多片） */
    CA_EV_TOOL_CALL_END,  /* 参数收齐 */
    CA_EV_USAGE,          /* token 用量（如服务提供） */
    CA_EV_ERROR,          /* 服务端返回的错误 */
    CA_EV_DONE
} ca_event_kind;
```

上层**不得**知道底层是哪家协议。这条是 US-8 的实现基础。

## 5. 工具协议

### 5.1 工具清单（v0.1 完整）

| 工具 | 用途 | 默认权限 |
|------|------|----------|
| `read_file` | 读文件，按字节截断 + 行号 | 需确认（越权路径时） |
| `write_file` | 写/覆盖文件 | **需确认** |
| `edit_file` | 按精确匹配替换 | **需确认** |
| `list_dir` | 列目录 | 需确认 |
| `search` | 字面/正则搜索（ripgrep 式） | 需确认 |
| `run_shell` | 执行 shell 命令 | **需确认** |

### 5.2 权限模型（安全硬约束）

| 规则 | 内容 |
|------|------|
| P1 | **默认全部拒绝**。未经用户明确批准的调用不得执行 |
| P2 | 确认提示必须展示：工具名、完整参数、改动影响面（行数增减/受影响文件数） |
| P3 | 拒绝后必须向模型回灌结构化「已拒绝」结果，**不中断会话** |
| P4 | 路径必须规范化后落在工作区内；`..`、符号链接指向外部一律拒绝 |
| P5 | `run_shell` 必须展示**完整命令原文**，不得折叠或省略 |

> P4 的符号链接逃逸必须用真实用例覆盖——只测 `../` 不够，
> 符号链接是另一条路径，且更隐蔽。
>
> P2 的「完整参数」在 `write_file` 上有**展示上限**：内容超过 2048 字节时只展示开头，
> 并显式标注总字节数与省略量（把 1 MB 全量刷到终端没有信息价值；
> **不标注的截断**才是欺骗）。路径与总长度始终完整展示。

### 5.3 工具结果进入对话的格式

```
<result path="src/a.c" lines="1-80" total="1200" truncated="true">
...
（截断处插入显式标注，说明省略了多少行、如何获取剩余部分）
</result>
```

**约束**：结果**必须**携带来源元信息（路径/行范围/是否截断）。
模型需要知道内容是否完整，否则会基于残缺数据下结论。

## 6. 会话持久化

| 项 | 规定 |
|----|------|
| 位置 | 用户配置目录下的 `cagent/sessions/<id>.json`，不写工作区 |
| 具体路径 | Windows `%APPDATA%\cagent\sessions`；POSIX `$XDG_CONFIG_HOME/cagent/sessions`（缺省 `~/.config/cagent/sessions`） |
| 格式 | 单文件自包含，**单文件大小硬上限 4 MB**（与 §2.1 预算一致） |
| 写入 | **先写 `.tmp` 再 `rename`**：中途失败留下的临时文件不得顶掉一份好会话 |
| 列表 | 扫描目录，按修改时间从新到旧排序；损坏文件**照常列出并标注**，不得导致启动失败 |
| 恢复 | 读取时同样受 4 MB 上限约束；超出按 §2.1 的轮次淘汰规则截断 |
| 会话 id | 保存时自动生成（时间 + 进程内序号），并写回 `session->id` |
| 删除 | `<dir>/<id>.json`；id 含路径分隔符或 `..` 一律拒绝（`main` 会把它直接透传进来） |
| 密钥 | **绝不写入**会话文件（PRD NFR-3） |
| 落盘时机 | 每轮对话成功后立即落盘 + 退出时补一次：崩溃至多丢一轮，而不是整段对话 |
| 降级 | 取不到配置目录时**不报错**：仅在内存里记住，并在启动/退出时如实说明「不会落盘」 |

> **「损坏文件跳过并提示」的措辞修正为「照常列出并标注」**：静默跳过时，
> 用户在 `/list` 里看到的只是「会话不见了」，而原因（文件损坏）其实可查。
> 标注 `[损坏，已跳过]` 既完成提示，又保留了可发现性。`/resume` 一个坏 id
> 返回失败提示且**不做任何改动**——不顺手删掉用户可能还想自己看的文件。

**会话历史保存什么、不保存什么**（边界，避免被误读成「完整对话记录」）：

- 保存 `user` 消息与助手**文本**回复；淘汰按整轮（§2.1）进行。
- **单次输入内部的工具调用回合（tool_calls / tool 结果）不跨输入保留**：
  它们只活在当次 `core` 循环里（上限 `CA_CORE_MAX_TOOL_ROUNDS`）。

## 7. 终端界面

| 项 | 规定 |
|----|------|
| 原始模式 | 必须同时支持「原始模式不可用」的降级路径（如管道输入、CI 非 TTY） |
| 流式渲染 | 逐 token 追加，**不做全量重绘**（重绘是卡顿的主因） |
| 确认交互 | 就地渲染提示并等待输入；不得在渲染中途清屏导致用户看不到待批准内容 |
| 非 TTY | 管道/CI 场景自动降级为行式输出，不尝试原始模式 |

> 「原始模式不可用时怎么办」必须有测试覆盖——CI 跑测试时就是非 TTY，
> 这条不测就会在 CI 上炸。

## 9. 违约判定

以下任一情况视为违反本契约，G2 不得通过：

| # | 违约 |
|---|------|
| V1 | 传输层存在「读全量响应」接口 |
| V2 | 任一分层可无上限增长（无字节上限的累积容器） |
| V3 | 引入第三方 JSON 库 |
| V4 | 工具调用存在「默认放行」路径 |
| V5 | 路径逃逸未被拒绝（含符号链接） |
| V6 | 会话历史无字节上限 |
| V7 | 平台差异泄漏到 `core` / `llm` / `tools` |

## 10. 测试要求（契约级）

| # | 要求 |
|---|------|
| T1 | 每个内存预算都有对应的**边界用例**（恰好超限、远超限） |
| T2 | 传输层须有「永不整块缓冲」的测试：用超大响应流验证 RSS 增量受控 |
| T3 | 会话历史封顶须有测试：灌入超限历史后断言淘汰发生且**UI 有明示** |
| T4 | 权限拒绝路径须有测试：拒绝后断言会话**未中断**（P3） |
| T5 | 非 TTY 降级路径须有测试 |

> T2 是本契约最重要的一条测试。它直接对应 PRD 风险 3 与 4——
> 若实现里混入了整块缓冲，T2 必须先红。
