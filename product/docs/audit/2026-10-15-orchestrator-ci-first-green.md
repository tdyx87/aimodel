## 1. 基础信息

| 字段 | 内容 |
|------|------|
| 角色 | `orchestrator` |
| 时间 | 2026-10-15 |
| 任务 | CI 首次真正跑通后，核对并修正此前基于「无法验证」得出的全部判断 |

## 2. 背景：此前的信息基础

在 `94e4cfa` 之前，以下判断在文档里被当作事实：

- 「POSIX 专有代码从未被编译过，当前判断其『大概率可编译』缺乏依据」
- 「Linux / macOS 产物无法生成，无法验证」
- 「本地编译零告警」
- 「三平台均未验证」

这些判断的共同点：**它们描述的是「本机无法验证」，却被写成了产品事实**。
本审计要做的不是补充新结论，而是**把「没验证过」与「验证了不行」区分开**。

## 3. 首次实测结果（`94e4cfa`）

| 平台 | ctest | pytest | 产物 | 产物 E2E |
|------|-------|--------|------|----------|
| windows-latest | 44/44 | 46 passed, 2 skipped | NSIS + ZIP | 6 passed |
| ubuntu-latest | 44/44 | 46 passed, 2 skipped | DEB + TGZ | 6 passed |
| macos-latest | 44/44 | 46 passed, 2 skipped | DMG + TGZ | 6 passed |

**逐条核对方式**：拉取三个 job 的原始日志，核对测试计数与产物路径，
**不依赖「步骤状态为绿」推断**。`2 skipped` 已查明是产物 E2E 的两条运行级用例
（打包前无产物故跳过，打包后独立执行并通过）。

## 4. 被推翻的判断

| # | 原判断 | 实测 | 教训 |
|---|--------|------|------|
| 1 | POSIX 代码可能编不过 | 一直能编 | 「没验证过」不等于「有问题」。把前者写成后者，是文档失实的开始 |
| 2 | Linux 产物无法生成 | DEB/TGZ 正常产出 | 同上 |
| 3 | macOS 产物无法生成 | DMG/TGZ 正常产出 | 同上 |
| 4 | 本地零告警 | 每次构建都有 `warning LNK4044` | 我筛选告警的 pattern 只匹配 `error C\|warning C`，漏掉了 LNK 前缀。**据此说过多轮「零告警」，那句话是错的** |
| 5 | 三平台均未验证 | 三平台全绿 | 前四条是这个结论的基础，基础错了结论就错 |

> 第 4 条的教训与 ADR-0001 §6.3 记录的 JSON 断言问题是同一类：
> **验证手段本身有盲区，而「验证通过了」的印象掩盖了盲区的存在。**
> 那次是 `find()` 挡不住漏引号，这次是 pattern 挡不住 LNK 告警。

## 5. CI 挖出并已修的五个真实缺陷

按「被前一个修复暴露」的顺序排列——**没有一个是主动发现的**：

| # | 缺陷 | 首次暴露于 |
|---|------|-----------|
| 1 | 工作流 `shell: ${{ matrix.shell }}` —— step 级 `shell` 不在 `matrix` 白名单 | 语法错误，用户报 |
| 2 | `CMakeLists.txt` 无条件设 `-static-libgcc -static-libstdc++`（MinGW 专属泄漏） | 修复 1 后 macOS 配置失败 |
| 3 | CI 硬钉生成器 `"Visual Studio 17 2022"`，运行器镜像已无此版本 | 修复 1 后 Windows 失败 |
| 4 | 产物 E2E 只找 `*.zip`，Linux/macOS 的 CPack 不产 ZIP | 修复 2/3 后 Ubuntu E2E 失败 |
| 5 | 产物 E2E 用 `rglob` 匹配到 CPack **暂存副本** | 自查时发现（实测顶层 ZIP 挪走后仍 2 passed） |
| 6 | 把「获取 NSIS」设为打包硬前置，Chocolatey 504 即拖红整条 Windows 腿 | 修复后自暴 |

### 5.1 两个值得单独记的

**缺陷 5 是本轮最隐蔽的一个。** 产物 E2E 用 `rglob("*.zip")` 匹配到
`_CPack_Packages/win32/ZIP/` 里的同名暂存副本。后果：最终产物缺失、损坏、
或压根没重新打包时，用例照样在旧副本上跑通并**显示绿色**。

它与我刚加的「缺产物即 fail」机制直接冲突——我加了 fail 模式，
但查找器挑错了对象，于是 fail 模式**形同虚设**（实测验证）。

> 「找不到就跳过」的逻辑一旦挑错对象，症状不是失败，而是**安静地验证了错的东西**。
> 因此查找逻辑本身必须有测试——该文件此前一条都没有。

**缺陷 6 是依赖层级错误。** 产物 E2E 只解压 ZIP/TGZ，NSIS 产出的是安装器，
两者不冲突也不互相依赖。为让 E2E 能跑而强制依赖一个外部包源，
是把「顺带验证」当成了「前置条件」。结果 Chocolatey 源一次 504 就拖红整条腿。

改为：先试完整 `cpack`，失败才降级为只产 ZIP，并发 `::warning::`。
**降级必须出现在日志里，不静默**——否则又回到「零覆盖却显示全绿」。

该改动同时修掉一个我自己引入的误判：原先用 `command -v makensis` 预先判断，
但 CPack 找 NSIS 不只看 PATH，还查 Windows 注册表（本机 makensis 就不在 PATH 里，
CPack 却照样打出安装器）。照 PATH 判断会误报「不可用」，白白降级掉可产出的安装器。
**改为让 CPack 自己决定。** 事实证明这一改动是对的：CI 上 Chocolatey 失败，
但 CPack 从注册表找到 NSIS，NSIS + ZIP 双双产出。

## 6. 仍然不成立的

诚实记录，避免「三平台全绿」被读成「三平台可发布」：

| # | 项 | 状态 |
|---|----|------|
| 1 | Linux 的 **DEB 装到干净容器后能启动** | 未验。产物 E2E 解压 TGZ 跑二进制，不等于安装路径可用 |
| 2 | macOS 的 **DMG 挂载后 .app 能启动** | 未验，同上 |
| 3 | macOS / Linux 的**卸载/回退** | 未验 |
| 4 | 代码签名、公证、自动更新通道 | 仍受阻（外部依赖） |
| 5 | 大存档内存占用（99 MB → 420 MB） | 已知限制，修它需改冻结的契约 §3.2 |

**「三平台编译测试打包全绿」与「三平台可分发」之间，差的就是第 1~3 项。**

## 7. 对框架实验的影响

本次是「角色系统能否用于游戏领域」这一实验的关键补充：

| 观察 | 结论 |
|------|------|
| 跨平台验证需要真机吗 | **需要 CI，但 CI 也会骗人**：静态校验错误会伪装成「测试失败」，包源抖动会伪装成「代码问题」，暂存副本会伪装成「产物正常」 |
| 只读角色的价值 | 本轮 `release-engineer` 此前记录的「⛔ 无法生成」「可能编不过」**全部被证伪**。它当时的写法是诚实的（标了受阻），但**文档把「未验证」渲染成了「不可行」**——这是发布检查单的表达缺陷，不是角色的判断缺陷 |
| 最大的收益（更新） | **「未验证」与「验证了不行」必须在文档里可区分**。ADR-0001 的 ❓/⛔ 分档正是为此设计，本轮提供了第一组真实数据 |
| 最大的短板（更新） | 门禁要求「检查单全绿」，而检查单会把「没验过」和「不行」混写，导致门禁无法判断该做什么 |
