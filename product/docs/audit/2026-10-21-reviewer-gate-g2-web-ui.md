## 2. 审查清单

| # | 检查项 | 结论 | 依据 |
|---|--------|------|------|
| R1 | 是否引入**新依赖** | 通过 | 仅 Windows 的 `ws2_32`（socket）与 `bcrypt`（系统熵），都是系统 DLL；无第三方库。CI 三平台会编 |
| R2 | 平台差异是否仍收在 `web_net.c` | 通过 | `web.c` / `web_page.c` 里没有 `#ifdef _WIN32`；契约 §8 满足 |
| R3 | 结构化事件是否会**阻塞**代理 | 通过 | 事件回调只做格式化与入队，不做 I/O；`ca_web_emit` 内部有超时（见 R4） |
| R4 | SSE 写客户端会不会**拖住代理** | 通过（评审前已修） | 原实现持全局锁做阻塞写，客户端不读就卡住代理；现改为「快照 + 引用计数 + 放锁后写」，并给 socket 设 `SO_SNDTIMEO=2s` |
| R5 | fd 复用是否会导致**事件写错客户端** | 通过（评审前已修） | 原实现 SSE 处理器直接 `close(fd)`，而此时可能正有线程在写 → fd 被新连接复用后事件泄露。现有引用计数：关闭前等 `refs==0` |
| R6 | 令牌校验是否有绕过路径 | 通过 | `/api/*` 一律要求 `X-Cagent-Token` 头或 `?t=`，比对失败即 401；`GET /`（页面本身）不需要令牌（页面里没有敏感数据） |
| R7 | Host 头校验是否有效 | 通过（评审前已修） | 原实现把第一个 CRLF 换成 `'\0'`，整个头部块被截断 → 头一个都扫不到（带令牌也 401）。现请求行单独取副本，头部原样保留 |
| R8 | 是否有**未受限**的资源 | 通过 | 活跃连接 64（每连接一线程）、SSE 客户端 32、请求头 8 KB、请求体 64 KB、消息队列 32×8 KB、工具结果沿用 1 MB 上限 |
| R9 | 消息通道是否可能**丢消息** | 通过（有记录） | 队列满时返回 503「queue full」而不是静默丢弃；`ca_web_push_user` 返回值被检查 |
| R10 | 事件载荷是否可能**截断成非法 JSON** | 通过 | 载荷装不下时显式降级为一条短消息（半截 JSON 会让浏览器 `JSON.parse` 直接失败，页面卡死） |
| R11 | Web 模式下**批准通道**是否仍然必经用户 | 通过 | 浏览器批准走 ui 层的输入源（`read_byte`），与终端同一套逻辑；`run_shell` 仍需 `CAGENT_ALLOW_SHELL=1`（main_perm 未改） |
| R12 | 终端模式是否**未受影响** | 通过 | `cfg.on_event` 为 NULL 时 core 行为完全不变（所有发事件处都判空）；`ctest` 8/8 全绿 |

## 3. 遗留（记录，不阻塞）

- SSE 不做 keep-alive 复用：每个请求一条连接（只有 SSE 例外）。简单可预测，代价是每个请求一次 TCP 握手（本机回环，可忽略）。
- 不支持分块编码与压缩：浏览器发分块请求体会被忽略（Content-Length 缺失 → body 视为空）。本地 UI 不受影响，但记在这里。
- 页面内嵌在二进制里：改 UI 需要重新编译。可接受（UI 改动不频繁）。
- Web 模式暂不支持 `/list` `/resume`（只支持 `/new` `/exit`）。

## 4. 结论

新能力按契约实现，四条安全闸（回环监听 / 随机令牌 / Host 校验 / run_shell 显式开启）都在，
且三个「评审前自查发现」的真问题（SSE 截断丢事件、头部截断导致带令牌也 401、fd 复用泄露）
已修并复验。✅ 通过，放行 G3。
