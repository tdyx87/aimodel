## 4. 关键决策

| 决策 | 理由 | 被否决的备选 |
|------|------|--------------|
| E2E 分两级验证：路径 1 用**真实浏览器 DOM**，路径 2~5 用 HTTP 集成 | 环境无 Playwright/Selenium，`--dump-dom` 无法触发 file input。但「页面能否在浏览器里正确渲染出首屏」是真实浏览器问题，值得单独验；其余路径的数据契约 HTTP 层即可覆盖 | 全部 HTTP 级（丢掉了浏览器渲染验证）/ 全部浏览器级（做不到） |
| 判定 DOM 正确性看**内容**而非浏览器退出码 | Edge 加 `--dump-dom` 后不自行退出（profile 锁），此前曾误判为失败。DOM 已完整落盘就该算数 | 断言退出码（会把通过判成失败） |
| E2E **不依赖子进程 stdout 解析端口** | Windows 上重定向的 stdout 是块缓冲的，程序不显式 flush 时端口行永不落盘，`readline()` 永久阻塞——本项目实测卡死 30 分钟 | 解析 stdout（已踩坑） |
| 自己挑空闲端口 + 轮询 TCP 连接 | 同上，且不依赖子进程的输出行为 | `--port 0` + 解析输出 |
| 用 Python 生成的样本作为 E2E 输入 | 同时闭环「跨语言一致性」缺口：样本由参考实现生成，断言的是 C++ 侧解析结果，两侧一致即等价于交叉验证 | 另造一套 C++ 样本（与真实格式脱钩） |
| 并发用例拆成「并发读」「并发写」两条 | 首版只有并发读，而真正的数据竞争发生在**并发写**。并发读全绿但问题仍在——**那是有假安全感的用例**，已在策略 §5 记录 | 只有并发读（正是被 security-reviewer 打回的原因之一） |
| 断言用户可见结果，不断言内部字段 | 如「槽位 2 的数据已被改动」出现，而非「`ParseSlotData` 被调用了一次」 | 断言实现细节（会阻碍合法重构） |

## 5. 风险与阻塞

### 5.1 E2E 抓出的真实缺陷（本角色的主要产出）

**缺陷 1：`/api/save/slot` 返回非法 JSON —— 槽位详情页完全打不开**
- 服务端拼成 `{"ok":true,{"slot":1,...}}`，前端 `response.json()` 抛异常
- **为什么前三层测试都没抓到**：
  | 层 | 漏因 |
  |----|------|
  | 库层单测 | 没有 HTTP 拼装；`SlotToJson` 的返回值本身合法 |
  | HTTP 层单测 | 只测了 `/api/save/slots`（数组拼接合法），没测 `/api/save/slot`（对象拼接非法） |
  | 前端 | 免构建形态下无 JS 测试层（既定取舍） |
- **两个测试都通过，功能却是坏的** —— 这是「用户场景 E2E」不可替代的直接证据
- 已修复，并新增 `test_slot_endpoint_returns_wellformed_json` 作回归哨兵

**缺陷 2：打开失败后服务端仍保留上一个存档的数据**
- 界面已切到诊断视图，但 `/api/save/slots` 仍返回旧存档槽位 → 服务端状态与界面所见不一致
- 已通过 `SaveInspector::Clear()` 修复，由 `test_unparseable_...` 断言打开失败后返回 409

### 5.2 未覆盖项（如实登记，未粉饰为通过）

| 项 | 原因 | 后果 |
|----|------|------|
| **Linux / macOS 三平台验证** | 本环境仅 Windows | `save_file_posix.cpp` / `local_http_posix.cpp` 的路径、宽字符、socket 行为**从未被运行过**。`roles.md` §3.8 要求三平台验证——**该完成标准未满足** |
| DOM 交互流（点 file input → 上传 → 点卡片） | 无浏览器自动化框架 | 已验证的等价物：真实浏览器渲染首屏 + HTTP 层走完数据路径。**不等于**验证了点击流 |
| ThreadSanitizer 下的竞态证明 | 构建成本高 | 并发写用例是回归哨兵，不是竞态的证明 |
| 超大文件（>512 MB）端到端行为 | 测试环境不便生成 | 上限校验有单测；端到端行为待专门环境验证 |
| 空槽位判定启发式 | 契约无 `is_empty` 字段 | 见 `frontend-implementer` 审计 §5，未闭环 |

### 5.3 测试本身的缺陷（已修）

| 缺陷 | 后果 |
|------|------|
| E2E 首版 `Send(head, n)` 填的是 n 个 `'x'` 占位字节而非真实内容 | 服务端自然解析失败，用例却断言 200 → **测试在说谎**。已改为发送真实 body |
| 「打开成功」与「业务成功」混为一谈 | `/api/save/open` 对业务失败也返回 200。首版仅断言状态码，把「成功」与「失败」都判成通过。已改为断言响应体 |
| `test_close_per_request_premise_holds` 依赖前序用例状态 | 前序用例清空存档后返回 409 而非 200 → 顺序耦合。已改为用静态资源 |
| `FormatTimestamp` 期望值凭印象写 | 实测 `1773500000` → `2026-03-14 14:53`（我原写 21:06）。已改为独立核算后的正确值 |

> 记录这四条不是为了好看，是因为它们都属于同一类问题：**验证手段本身没被验证**。
> 其中「E2E 填占位字节」最严重——它让整条主路径看起来是绿的。
