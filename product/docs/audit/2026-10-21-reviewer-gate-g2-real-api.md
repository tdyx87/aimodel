## 2. 审查清单

| # | 检查项 | 结论 | 依据 |
|---|--------|------|------|
| R1 | 请求体 JSON 是否**结构正确**（`tools` 挂载位置） | 通过 | 拼装顺序为「关 messages 数组 → `,"tools":<json>` → 关根对象」。顺序错误会拼出 `{...,"tools":[...]]}`，服务端 400 且错误体为空（真实故障现场）——已按此顺序实现 |
| R2 | 工具参数名是否与实现解析的键**一致** | 通过 | 逐个对照实现：`read_file(path/offset/limit)`、`write_file(path/content)`、`edit_file(path/old_string/new_string/replace_all)`、`list_dir(path)`、`search(pattern/glob/max_results)`、`run_shell(command/timeout_ms)`。名字写错的表现是「模型照错名字调用 → 工具总是失败」，且不会有任何报错 |
| R3 | `raw[256]` 是否违反契约 C1 | 通过 | 定长 255 字节，与响应大小无关；`on_data` 里一旦装满就不再记录。C1 禁止的是「按响应大小增长的缓冲」，这里不存在 |
| R4 | 工具结果回灌的**措辞**是否会误导 | **发现问题，已修** | 原实现对「已执行」和「被拒绝」用同一句 "already been executed"。被拒的工具**并没有执行**，那句话会让模型以为文件已经写好——正是最坏的结果。已按 `ca_tool_status` 分成两句（denied 时说明「did NOT run、不要重试」），并补了两条用例 |
| R5 | 4xx 原因提取是否会**误取** | 通过 | 只认 `"message"` 键；取不到就退化为纯文本片段（换行压空格），再取不到用通用文案。不会把响应里的任意片段当「原因」 |
| R6 | 状态码解析是否覆盖**重定向/多状态行** | 通过 | `header_cb` 解析 `HTTP/x.y NNN`；`curl_easy_perform` 之后以 `CURLINFO_RESPONSE_CODE` **覆盖**（libcurl 的值才是权威）。两层并存不会出错 |
| R7 | 是否存在**双重打印** | 通过（已修） | `main` 与 `core` 都打印过错误，真实输出里同一错误连出两行。已删 `main` 的打印（`core` 有 `last_error`，信息更全） |
| R8 | 错误信息里会不会**泄露密钥** | 通过 | 错误体只取 `message` 字段与纯文本片段，不打印请求头；会话文件不含 key（已核对） |
| R9 | 工具结果回灌是否应改为 `role:"tool"` + `tool_call_id` | **未采纳（遗留项）** | 这是正解，但需同时回带 assistant 的 `tool_calls`、扩展消息结构与序列化（约 200 行且动会话导出）。本轮用「已执行/被拒绝」措辞缓解，重复调用已明显减少。**已登记为遗留项**，不阻塞 |
| R10 | `search` 新入口的**权限**是否与其他工具一致 | 通过 | `ca_tool_search_json` 只做参数解析，仍走 `ca_tool_search` → 内部同样走权限回调（tools 层统一入口） |
| R11 | 新增测试是否**能证伪** | 通过 | 把 core 的请求改成不传 tools → `core_offers_tools_to_the_model` 立即 FAIL（exit 1）→ 恢复后转绿。另两条新用例锁定「已执行/被拒绝」措辞 |
| R12 | 文档与实现是否一致 | 通过 | 契约 §5.1 补「工具必须真的出现在请求里」与 `search` 可达性；§5.3 补回灌形式与遗留项；README 补真实服务自检与「未验证」清单更新 |
