## 2. 关键决策

### D1. 打印分两层：默认给「完整请求体 + 完整模型输出」，原始帧另开开关

| 开关 | 打印什么 | 默认 |
|------|----------|------|
| `CAGENT_TRACE=0` 关掉 | — | **默认开** |
| `CAGENT_TRACE_RAW=1` | 额外逐帧打印**原始协议帧** | 默认关 |

- **理由**：模型回一句话往往就是**上百帧**（每 token 一帧）。逐帧打印会把终端刷爆，
  正文反而看不见 —— 那等于没打印。
  而「模型看到的完整历史」与「模型说的完整话」才是排查问题时真正要看的东西。
  原始帧（`tool_calls` 的 id、arguments 的分片、错误体）是**协议层**的证据，
  需要时再开。
- **否决的备选**：只打印原始帧。理由同上——噪音掩盖了正文。

### D2. 请求体在**历史淘汰之后**才打印

core_one_turn 里请求体可能被淘汰机制改写（丢掉最旧的完整轮次后重试）。
只有**最终**这一份才是服务端真正收到的。在构造完就打印，打印的是**没发出去的那份**。

### D3. 打印的是**原文**，不做任何加工

新增 `ca_ui_dump(ui, title, text)`：逐行原样输出，不折行、不缩进、不替换字符、
**不截断**。理由是「看到的就是真正发出去的」——
一旦在这里偷偷加工，用户排查时看到的就是被加工过的东西。

- **顺带修掉的 UI 隐患**（都实测过）：
  - 标题会粘在模型**正在流式输出**的那句话后面（`…模型说的话标题`）。
    现在 dump 前先把当前行闭合。
  - 截断路径不写 NUL 结尾 → 序列化器按 C 字符串读会越界。

### D4. 模型输出用**定长缓冲**（64 KB）攒完整文本，一轮结束再打印一份

- 流式输出是「正在打字」的效果，屏幕上留不下**可复制的完整文本**。
  所以在 core 里另攒一份完整副本，一轮结束时打印。
- 定长上限 64 KB，超出**显式标注**并停止累积（不静默截断）——
  一份被悄悄截断的「完整输出」比没有更糟。
- **不违反「不整块缓冲」**：契约 C1 限制的是**传输层**不得提供「读全量响应」的接口；
  这里攒的是**文本**且有上限，且仅在 trace 开启时使用。

### D5. 请求体里**没有** API key，所以原样打印不会泄露密钥

key 在 `Authorization` 头里，不在请求体里。这条要**说清楚**——
否则「打印请求体」听起来像个危险动作。

### D6. Web UI 的三个问题都是**结构**问题，不是「调 CSS」

逐条定位（每条都在真实浏览器里复现并验证）：

| 现象 | 根因 | 修法 |
|------|------|------|
| **滚动条不对** | `#log` 只是普通 div，页面随内容变长 → 滚动条属于**整页**；且 `#log` 作为 flex 子项**没写 `min-height:0`**，内容把它撑破 → 它根本不滚动 | `body` 改成 `100vh` 的 flex 列；`#log` 独占剩余空间并自己滚动；**`min-height:0`**（flex 子项默认 `min-height:auto`，这是最经典的坑） |
| **不自动滚动** | 追加内容后**才**判断「离底部多远」：此时 `scrollHeight` 变大了、`scrollTop` 没动 → 距离超阈值 → 判定成「用户不在底部」→ **一次都不跟** | 判断挪到 DOM 变更**之前**；再用**滚动方向**做主判据（用户真的往回滚才取消跟随） |
| **不美观** | 每个 token 一个 `<div>` → 一次回答变成几十个方块；工具的「执行中」与「完成」各建一张卡 → 同一个工具出现两次 | 同一段回复合并进**同一个**气泡；工具结果**更新同一张卡片**；另有配色/圆角/留白/等宽输出/长输出折叠/空态提示/响应式等重做 |

### D7. 跟随状态用**方向**判断，而不是只看位置

只用「离底部多远」判断跟随，会被**布局变化**误伤：输入框复位、消息区长高等，
都会让 `scrollHeight` 与 `clientHeight` 的关系变化 → 误判成「用户上翻了」→
**从此再也不跟随**。

改成：用户往回滚（`scrollTop` 变小）才取消跟随；滚回底部或内容增长则恢复。
另外把「输入框复位」挪到追加消息**之前**，让布局先稳定下来。

### D8. CI 里没有浏览器，所以把结构不变量**写进冒烟脚本**

`scripts/web_smoke.py` 增加 5 条静态检查（`min-height:0`、`overflow-y:auto`、
有 `push(`、不再用 `position:sticky`、有气泡合并逻辑）。

- **理由**：结构改错了单测不会红，但用户一眼就看出来。
  既然 CI 里跑不了浏览器，至少把「改回来就会红」的不变量钉住。

## 4. 术语与实现边界（如实记录）

### 实现期踩到的两个**真 bug**（都是我自己写的第一版）

**（1）自动滚动一次都没生效过。**
第一版在追加内容**之后**判断「离底部多远」。此时 `scrollHeight` 已经变大、
`scrollTop` 还没动 → 距离超过阈值 → 判定成「用户不在底部」→ 不再跟随。
浏览器实测：连发 10 条消息后底部间隙 1819 px。

**（2）跟随状态被布局变化误伤。**
第二版改成「追加前判断」，但输入框复位（`input.style.height='auto'`）
发生在追加**之后** → 消息区长高 → 位置关系变了 → 判定成「用户上翻」→
**从此再也不跟随**。浏览器实测：间隙 1126 px。

最终版用**滚动方向**做主判据，并把输入框复位挪到追加之前，才真正稳。

> 教训：自动滚动这类「跟随」行为，难点不在滚动本身，而在**怎么区分
> 「用户主动离开」与「布局自己变了」**。只看位置必然误判。

### 尚未覆盖（如实记录，不假装支持）

- **Web UI 的 trace**：终端里有完整打印，**浏览器里没有**。
  Web 模式的事件里没有「原始请求体」这一类，补它要动 core 的事件协议
  （新增事件类型 + web.c 映射 + 页面渲染），本轮没做。
  终端输出在 Web 模式下**仍然可见**（同一个进程的 stdout）。
- **`tools_test` 的界面部分**：CI 没有浏览器，界面的**行为**靠
  `web_smoke.py` 的静态检查 + 本轮的**真实浏览器验证**覆盖，
  浏览器验证过程没有进 CI（CI runner 上没有可交互浏览器）。
- **长输出的折叠阈值**（600 字符）是拍脑袋定的，没做用户验证。
