## 4. 关键决策

| 决策 | 理由 | 被否决的备选 |
|------|------|--------------|
| **PRD §5「格式由谁提供」定为：架构层固化自有格式** | 若依赖外部格式，可用性完全受制第三方，且 PRD 阶段无法确定验收基线。自有格式可完整覆盖 US-1~US-3 所需字段与全部损坏场景 | 等待外部格式规范（阻塞 G1）；采用通用格式如 zip+json（无法表达损坏场景，诊断需求落空） |
| 格式定为**多槽位 + 槽位表 + CRC64**，而非单块 blob | 槽位表让「部分损坏仍可用」可实现——单槽损坏时其余槽位仍可读，这是 US-3 的硬要求 | 单块二进制（一个字节错则全盘不可读，US-3 无法满足） |
| 每槽位独立校验和，而非全文件一个 | 损坏能被**定位到具体槽位**，直接支撑 US-5 的「哪里坏了」 | 全文件单一校验和（只能答「文件坏了」，无法答「哪里」） |
| 对外 API 用 `bool` + 输出参数，不返回异常 | C++11 无 `std::expected`；且契约要求「任意字节不得抛未捕获异常」，`bool` 语义比异常更可控 | 返回 `optional`（C++17）/ 抛异常（需全链路 catch，易漏） |
| 解析失败产出**结构化诊断列表**而非单个错误串 | US-5 要同时回答「哪 + 为什么 + 做什么」，且多槽位可能同时有多处损坏；单串表达不了 | 单个 error string |
| 业务失败回 `200 + {ok:false,diagnostics}`，传输错误才用 4xx/5xx | 「存档损坏」是**可预期的业务结果**，不是协议错误；前端需要拿到结构化诊断数组 | 损坏一律 4xx（前端仍要解析 body，语义混淆） |
| 复用 aimodel 的本地 HTTP + 同源端点形态 | 免构建静态页（`roles.md` §3.5）下没有 CORS 之外的替代通信方式；沿用已验证可行的形态 | 用自定义二进制协议（需前端建 WebSocket/自定义帧，复杂度与收益不匹配） |
| 对外 API 设计为**格式无关**（新增格式只加适配器） | 兑现 §2 的扩展性承诺，避免未来支持新格式时 breaking change | 每版本一套 API（接口爆炸） |
| 只读保证设计为**API 层面不提供写入入口** | NFR-5 的硬约束。`security-reviewer` 可用「产物中不存在写入路径」这一可判据核验，比口头承诺强 | 提供 `SaveFile::Write()`（与 NFR-5 冲突） |

## 5. 风险与阻塞

> 以下两项在首次提交时已自行登记，并经 `orchestrator` 打回；**返工补齐情况见 §5.1**。

- ~~**CRC64 实现待定**：契约要求跨平台一致，但未指定变体。三平台各自实现会得到不同的校验值，同一存档在不同机器上诊断结果相反。~~
  → **已解决**：新增 §2.1.1 固定为 CRC-64/ECMA-182（多项式 `0x42F0E1EBA9EA3693`、无反射、init/xorout 均为 0），并给出 `"123456789"` → `0x6C40DF5F0B497347` 的强制测试向量。
- ~~**道具 ID → 名称映射归属未定**：接口稿只给了 `{id, count}`，而界面稿要求前端展示名称。~~
  → **已解决**：`Item` 增加 `std::string name`，由核心库填充（映射表留在核心库内部），未知 ID 回退为「道具 #ID」。

### 5.1 剩余风险（不阻塞 G1）

- 压缩/加密标记（`flags` bit0/bit1）本期只做**识别与提示**，不解压不解密。契约已写明，但需 `cpp-implementer` 严格遵守，否则易自行扩张（PRD §4 范围外）。
- `SaveFile::diagnostics` 同时承载「成功项」（如「已升级」）与「问题项」，语义略混。可接受，但实现时须确保 `Severity` 三档都真的用上，否则接口退化为「只有错误」。
- 导出接口未定义落盘目录与文件名规则（PRD §5 待确认项）。建议 `release-engineer`/`doc-engineer` 阶段前补，当前不阻塞实现（前端可先行下载到默认目录）。
