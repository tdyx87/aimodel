## 4. 关键决策

| 决策 | 理由 | 被否决的备选 |
|------|------|--------------|
| 设计取向定为「**诊断优先**」 | 用户是带着「我的存档是不是坏了」的焦虑来的。界面主角应是数据与状态，而非操作按钮 | 通用型文件查看器（把存档当普通二进制文件，用户仍看不懂） |
| 槽位卡片定义 **7 个状态**（healthy/degraded/corrupt/empty/hover/active/default） | PRD US-2 要求显示健康状态，US-3 要求部分损坏仍可用。若只分「正常/异常」两态，实现方无从判断「异常但仍可看」该如何表现 | 仅 normal/error 两态 |
| `SlotCard.corrupt` **必须可点击** | US-3 硬要求「部分损坏仍显示能读出的部分」。若设计上做成不可点击，等于把「整槽拒绝」写进实现 | 损坏卡片禁用（直接违背 US-3） |
| 损坏字段采用**就地标注**而非整块隐藏 | 用户需要知道「这里有东西但读不全」，而不是「这块不见了」。隐藏会让人误以为本来就没有 | 隐藏损坏区块 |
| 诊断条目定为**三段式且末段必须有** | US-5 硬要求回答「哪里/为什么/能做什么」。少一段就无法验收 | 两段式（省地，但用户拿不到可执行动作） |
| `overall 损坏` 与 `部分损坏` 必须视觉区分 | 两者用户动作完全不同：前者只能重选文件，后者还可以继续浏览可读部分 | 统一显示为列表（用户会以为存档没事） |
| 沿用 aimodel 的深色配色 | 降低产品间割裂感；深色对长时间排查更友好 | 另起一套（无收益） |
| 拖放区必须同时提供点击与键盘入口 | 可访问性硬要求；且拖放在部分平台/输入法下不可靠 | 仅拖放 |
| 严重级用「图标+文字+颜色」三重表达 | 色觉障碍用户无法仅靠颜色区分损坏等级 | 仅颜色（WCAG 不合格） |

## 5. 风险与阻塞

- **道具名称依赖核心库字段**：本稿要求显示道具名。该依赖最初在契约中无对应字段，已由 `architect` 返工补上（`Item::name`）。**当前已解除阻塞**，但界面稿与契约存在跨文档耦合：若后续核心库未填 `name`，界面将显示空道具名——已在 `slot-detail.md` §4 注明归属。
- **导出落盘目录未定**（PRD §5）：影响 US-4/US-7 的落盘提示文案，暂按「由浏览器默认下载目录处理」表述。若 `release-engineer` 阶段改为指定目录，文案需同步。
- 界面稿以文字线框 + 组件规范形式给出，未提供像素级标注（尺寸/字号在设计系统 §3 已给字号与间距基数）。`frontend-implementer` 若需视觉稿，需追加一轮。
