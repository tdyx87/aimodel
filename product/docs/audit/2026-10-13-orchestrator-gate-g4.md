## 5. G4 裁决

| 项 | 内容 |
|------|------|
| 裁决 | ❌ **G4 不予放行** |
| 依据 | `roles.md` §4 的 G4 放行条件含「检查单**全绿**」，当前 6 项受阻；`roles.md` §3.11 的完成标准含「签名有效、更新通道可用」，两者均未满足 |
| 已达成 | Windows 侧**从源码到发布产物到产物级端到端**的全链路已验证；产品具备「内部/试用分发」条件 |
| 未达成 | Linux/macOS 编译与产物、全部代码签名与公证、自动更新通道 |

### 5.1 受阻项的性质区分

这一点对后续决策很关键，三类受阻完全不同：

| 类别 | 项 | 性质 |
|------|-----|------|
| **待验证** | Linux/macOS 编译与产物 | 工程问题，CI 已配置，结论即将可知 |
| **待投入** | 代码签名、公证 | 资源问题，需采购证书/开发者账号 |
| **待立项** | 自动更新通道 | 设计问题，当前**无任何相关代码**，不存在「做了没验」风险 |

### 5.2 可选处置（产品决策，非工程决策）

| 方案 | 内容 | 代价 |
|------|------|------|
| A. 试用分发 | 以内部/试用名义发布 0.1.0，不签名，明确告知使用者需在系统提示中选择「仍要打开」 | 零成本；但不可信分发，用户门槛高 |
| B. 先补 CI 结论 | 等 Linux/macOS 两项转绿，确认 POSIX 侧可编译可测试，再决定是否投入签名 | 零成本，只需等待 |
| C. 补齐后发布 | 配置证书 → 补 macOS/Linux 产物与冒烟 → 正式发布 | 需采购证书 + 异构环境 |

**建议 B → 再定 C/A。** 理由：签名的成本不可逆（年费），而 CI 结论即将到手；
在还不知道 macOS 能否编译的情况下先买证书，顺序是反的。

## 6. 本次验证实验的阶段性结论

四道门禁走完（`0319a5d` → `469db1b` → `679e12c` → 本轮），对「这套角色系统能否
用于游戏领域」的回答：

| 问题 | 结论 |
|------|------|
| 角色划分够用吗 | 够用。12 个角色在本次全部派上用场，无一是摆设 |
| 门禁有效吗 | 有效，且**有效性集中在设计审查与质量验证两端**：G1 打回拦住跨平台隐患，G2 拦住规范缺失，G3 拦下 3 个真实缺陷（其中一个是「测试都绿但功能是坏的」） |
| 只读角色价值高吗 | 高。`security-reviewer` 主动加严门禁条文并打回；`release-engineer` 拒绝把未签名的发布单写成全绿。**两次「本可放行但选择不放行」都是这两个角色做的** |
| 审计机制成本高吗 | 可接受。17 份审计 / 约 9000 行代码，比例约 1:530 |
| 最大收益 | **「文档步骤必须与实际界面一致」这类约束，只有 E2E 与门禁能强制。** 纯靠自觉，文档与产品会在第三次改动时脱节 |
| 最大短板 | **门禁本身没有「不可完成项」的出口。** G4 要求检查单全绿，但签名需要采购证书——这是外部依赖，不是工程投入。框架缺少一种「带明确受阻记录地阶段性放行」的机制 |

### 6.1 一个关于框架本身的发现

本轮暴露了一个 `roles.md` 的结构性缺口：**门禁条件默认所有条目都是可完成的**。
G4 要求「检查单全绿」，但「签名有效」在项目启动时就不具备条件（证书要花钱买），
而 G4 位于流程末端。到这一步才发现，等于前三道门禁的工作被一条外部依赖卡住。

这与我此前发现的另一处口径不一致（§3.8 完成标准 > §4 门禁条件）不同：
那处是**标准不一致**，这处是**标准缺少「受阻」这一档**。

两处都属不变层缺陷，本轮**未改 `.role-system/`**，仅登记于此。
若要修，建议的方向是：门禁条件允许「受阻项 + 明确记录 + 明确的阶段性放行裁决」，
而不是要求非黑即白。
