## 2. 范围决策及其后果

产品决策：**0.1.0 仅交付 Windows**，Linux/macOS 转为已知遗留，Windows 闭环后统一验证。

如实记录这条决策带来的四点后果，不因决策而美化：

| # | 后果 |
|---|------|
| 1 | 安装说明只覆盖 Windows；macOS/Linux 安装说明暂不提供 |
| 2 | CI 的 Linux/macOS 保持 `continue-on-error` 观察模式，**不作为放行依据** |
| 3 | 检查单 §2.3 / §2.4 / §4.5 由「⛔ 受阻」改标「⏭ 延期」 |
| 4 | **跨平台代码标准不降**：不得删 POSIX 分支、不得放宽 C++11、不得引入仅 Windows 可编的写法。延期的是**验证**，不是**要求** |

> 第 4 点是本复检的底线。范围决策可以改变「什么时候验」，不能改变「按什么标准写」。

## 3. Windows 侧本轮实际做了什么

上一轮 G4 时，Windows 侧存在一个**从未发现的缺口**：检查单 §4 标题写的是
「安装 → 首启 → 出结果」，但实际只验了 ZIP 免安装形态，**NSIS 安装形态从未跑过**。

本轮补齐，并实测两条 PRD 非功能需求（此前从未测过）：

| 项 | 之前 | 本轮结果 |
|----|------|----------|
| NSIS 静默安装 | **未验** | ✅ 退出码 0，落盘 `C:\Program Files (x86)\存档查看器\` |
| 已安装形态跑主路径 | **未验** | ✅ 从 Program Files 启动，`/` `/app.js` `/styles.css` 全 200；open→slots→slot→export 全链路 200 且返回真实槽位数据 |
| 卸载干净度 | **未验** | ✅ 目录完全移除、注册项清理、无残留 |
| 安装树无测试依赖 | 仅查过 ZIP | ✅ 安装形态亦无 gtest/gmock/Python |
| CLI 产物冒烟 | **未验** | ✅ 正常/损坏/不存在三种情形均正确，退出码正确，**错误信息不含用户路径** |

## 4. 本轮修复的真实缺陷

| 缺陷 | 影响 | 修复 |
|------|------|------|
| `Crc64Ecma182` 逐位实现 | 99 MB 存档解析 37.2 s，**NFR-2 违反的主因之一** | 改 256 项查表 → 24.8 s；契约向量仍通过 |
| Python 侧 `crc64_ecma182` 逐位实现 | 生成 100 MB 样本需 327 s，「验证大存档」本身不可行 | 同改查表 → 87 s |

**修复方式本身带来一条新增不变量**：查表是纯性能优化，写错会**静默产出错误校验和**，
而契约向量只覆盖单一输入，挡不住「只在某些输入上错」。故在
`tests/test_save_format.py` 新增 `查表版 == 逐位版` 等价性断言，覆盖 7 组长度与内容。

> 这是本轮唯一的编码改动。它不是为了「让测试变绿」，是为了让一个
> **此前从未被测量的需求**（NFR-2）有可对比的基线。修复后 NFR-2 **仍然不达标**。

## 5. NFR-2 不达标的处置

劣化曲线近似线性（≈0.35 s/MB、内存约 4×）：

| 存档 | 耗时 | 内存 |
|------|------|------|
| 2 MB | 0.45 s | 14 MB |
| 10 MB | 2.42 s | 48 MB |
| 50 MB | 11 s | 211 MB |
| 99 MB | 25~35 s | 383~411 MB |

按 512 MB 上限外推约 **180 s / 2 GB**。

四个处置选项（A 降低对外承诺 / B 摘要分页 / C 名字驻留 / D 大文件告警）
及各自代价已记入检查单 §6.2。**orchestrator 不代产品决策方拍板**，但明确两点：

1. 选项 A 属文档修正，**零代码风险，可立即执行**，且在任何发布动作前都应先做——
   当前文档对外宣称支持到 512 MB，与实测不符，这是**已存在的文档-事实偏差**。
2. 选项 C 会改动 G1 已冻结的契约 §3.2 结构，应作为独立议题走 ADR，不得顺手改。

## 7. 本轮暴露的第二个框架缺口

上一轮记录的框架缺口是「门禁没有『受阻』这一档」。本轮又暴露一个不同的：

> **门禁条件写的是结论（「检查单全绿」），而不是「该验证的都验证过了」。**

于是出现一个真实的漏洞：本轮发现 Windows 安装形态从未验证、NFR-2 从未测量——
但上一轮的检查单**仍然是诚实的**（它没声称验过安装形态），
**门禁却因为「签名未达成」而放不下，于是这两处缺口被签名问题一起盖住了。**

换言之：门禁在**应该拦**的地方拦住了（签名），但在**没拦住的地方也一并被忽略**了。
一个「整体不通过」的门禁，无法提供「哪些部分其实还没验」的信号。

与 §3.8 口径不一致（标准不一致）、与「缺受阻档」（标准缺一档）并列，
这是**第三类**问题：**门禁缺少分项结论**。

三处均属不变层缺陷，本轮**未改 `.role-system/`**，登记于此。
