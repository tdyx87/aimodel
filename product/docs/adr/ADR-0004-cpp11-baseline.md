# ADR-0004：语言基线从 C99 改为 C++11（静态链接运行时）

- 状态：**建议采纳**，待用户确认
- 日期：2026-10-19
- 相关：`docs/design/contract.md`（C99 约束）/ ADR-0003（**已于 2026-10-19 放宽到 100 MB**）

---

## ⚠ 预算放宽后，本 ADR 的结论随之变化

ADR-0003 决定把 NFR-1 放宽到 **100 MB**。这直接消解了本 ADR 最主要的推动力：

| 原建议（基于 8 MB 预算） | 放宽到 100 MB 后 |
|---|---|
| **必须**强制静态链接运行时 | 不再是硬需求 —— 动态链接的 2.2 MB 远在预算之内 |
| CI 需断言链接产物不含 `libstdc++.so` | 可以取消这项门禁 |
| 「切换要谨慎，因为触及核心卖点」 | 「切换的内存风险已大幅下降」 |

**也就是说：C++11 现在是一个便宜得多的决定。**
下面保留原始测量数据（结论仍然成立），但「强制静态链接」从**门禁**降级为**可选优化**。

---

## 背景

用户提出：JSON 层可以换成别的实现；且「C 版本可以使用 C++11」。

切换语言基线在本项目里不是小事 —— 它触及**项目最核心的卖点**（极低内存）。
所以先测量，再决定。和 ADR-0003 一样，不靠推测。

## 测量数据

全部为实测峰值 RSS（`/usr/bin/time -v` / Windows `PeakWorkingSet64`）。

### Linux（WSL2 / Ubuntu 18.04 / GCC 9.4）

| 程序 | 峰值 RSS |
|------|----------|
| 纯 C 空程序 | 1376 KB |
| C++ 编译但**不使用任何 STL 符号** | **1416 KB** |
| C++ + std::string/vector，**动态**链接 libstdc++ | **3620 KB** |
| C++ + std::string/vector，**静态**链接（`-static-libstdc++ -static-libgcc`） | **1388 KB** |

### Windows（MSVC 14.16）

| 程序 | 峰值 RSS |
|------|----------|
| 纯 C + `/MD`（动态 CRT） | 4272 KB |
| 纯 C + `/MT`（静态 CRT） | 3956 KB |
| C++ + `/MD` | 4272 KB |
| C++ + `/MT`（静态 CRT） | **3764 KB** |

## 结论

**C++11 这门语言本身几乎不要钱。**

- Linux：C 1376 KB → C++（不用 STL）1416 KB，**+40 KB**
- Windows：C（`/MT`）3956 KB → C++（`/MT`）3764 KB，**差异在测量噪声内**

**真正的开销是运行时的链接方式，不是语言。**

| 平台 | 动态链接运行时 | 静态链接运行时 | 差额 |
|------|----------------|----------------|------|
| Linux | 3620 KB | 1388 KB | **2232 KB** |
| Windows | 4272 KB | 3764 KB | 508 KB |

那 2.2 MB 与「用了多少 C++」无关 —— 它是动态库的映射、重定位表、
vtable、locale 表被触碰的开销。静态链接时链接器只保留真正引用到的目标文件，
其余部分根本不进二进制。

## 建议

**采纳 C++11。**（2026-10-19 更新：因 NFR-1 已放宽到 100 MB，
静态链接不再是硬门禁，降级为可选优化。）

- 语言本身在两个平台上都是**免费的**（+40 KB / 噪声内）
- 动态链接的 2.2 MB 在 100 MB 预算下无关紧要
- 若将来想再压内存，`-static-libstdc++` 是现成的开关，不必现在锁死

**不要**因为「省 2.2 MB」而在语言基线上做取舍 —— 那 2.2 MB
本来就不是这个决定的主要理由，主要理由是 RAII、类型安全、
以及少一类 C 才有的错误。

## 收益（不只是「换个语言」）

1. **RAII 消除手工 `free()`/`goto out`**。`tools_edit.c` 里那种
   三四个资源的失败路径已经出过一次错，这类结构在 C++ 里是自动的。
2. **类型安全**。`ca_json_cursor` 那类「结构体裸传 + 返回值语义不统一」的接口，
   在 C++ 里很难写出来。
3. **可以用 `std::string` / `std::vector`** 替代大量手写的定长缓冲，
   减少「缓冲区多大」这类反复出现的错误来源。
4. **`<regex>`** 可以补上 `search` 的正则部分（当前明确未做）。
   代价是 `std::regex` 本身很重，建议仅按需编译、且设上限。
5. **编译器支持更好**：本次 Linux 侧 12 条 GCC 告警、macOS 的 clang 差异，
   C++11 下这类问题更少。

## 风险与代价

| 风险 | 说明 | 缓解 |
|------|------|------|
| 二进制体积增大 | 静态运行时 | 对 RSS 无影响（本项目的门禁是 RSS） |
| 异常跨模块 | 静态 libstdc++ 的已知限制 | 本项目是单一可执行文件，不跨 DSO |
| **有人改成动态链接** | 悄悄超预算 2.2 MB | CI 加断言：检查链接产物里没有 `libstdc++.so` 依赖 |
| 改动面大 | 现有 10+ 个 .c 文件 | 逐层迁移，每层迁完跑测试，不一次性切 |
| 与 ADR-0003 叠加 | libcurl 已占 6 MB | 见下 |

## 与 ADR-0003 的关系

ADR-0003 指出 libcurl 已吃 6.04 MB，「空闲 ≤ 8 MB」不成立。
本 ADR 的结论是 **C++11 不会加剧这个问题**（静态链接下 +40 KB）。

但也说明：**真正的矛盾在 libcurl，不在语言。**
如果 ADR-0003 最终选了「按需 dlopen」或「放宽预算」，
本 ADR 都可以照常执行，两者不冲突。

## 需要决定的事

1. 静态链接运行时是否作为**硬性门禁**（CI 断言）？
2. 迁移方式：全部重写，还是**新增代码用 C++、存量 C 保留**？
   后者风险低得多，也符合本项目一贯的做法。
3. JSON 层是否顺势换成成熟实现？
   现在已定位并修复了野指针问题（`62e16e0`），短期没有换的**必须性**；
   但若转 C++11，换成 cJSON / yyjson 的成本会显著下降
   （不必再手写 `ca_json_cursor` 这一层）。
   注意：现契约 C6 要求「零分配」，换库需要同时改 C6。
