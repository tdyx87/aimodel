## 1. 背景

### 1.1 问题的来源

在「存档查看器」项目走 G4 时发现了这个缺口。过程如下：

1. G4 的放行条件之一是「`release-engineer` 检查单**全绿**」。
2. 实际检查单有 6 项受阻（签名、跨平台产物、自动更新通道等）。
3. 门禁判定不通过——**这一判定是正确的**。
4. 但同一轮复检中又发现：Windows 的 **NSIS 安装形态从未验证过**，
   PRD 的两条非功能需求 **NFR-1 / NFR-2 从未测量过**。
5. 这两处缺口**没有在门禁结论里单独出现**。

### 1.2 为什么它们被盖住了

关键在于：**上一轮的检查单本身是诚实的**。

它没有声称验过安装形态，也没有声称测过 NFR。把检查单逐行核对，
6 项受阻全部写明原因，无一项被勾成 ✅。按检查单自己的口径，它没有说谎。

问题出在门禁条件的**形式**上：

> 门禁问的是「检查单是否全绿」，这是个**单一聚合判断**。
> 一旦判定为不通过，「哪些部分其实还没验」这个信号就**不再单独输出**。

于是「签名没做」和「安装形态没验」被压缩成同一个「不通过」。
前者是**外部依赖**（要买证书），后者是**工程遗漏**（压根没做）——
两者的处置方式完全不同，却在结论里不可区分。

### 1.3 为什么这不是检查单的问题

检查单已经按规范记录了受阻项。问题在于：

**「受阻项」和「未验证项」在检查单里长得不一样，但在门禁结论里没有区别。**

- 受阻项：有条目、有状态标记（⛔）、有原因
- 未验证项：**没有条目**——因为从来没人写「安装形态冒烟」这一条

后者的危险在于：它不在任何清单上，所以任何针对清单的复核都发现不了它。
只有「复检时碰巧又去测了一遍」才暴露。

## 2. 决策

**门禁条件应要求「逐条分项结论」，不接受单一聚合判断。**

具体地：G1~G4 的放行条件中的每一项，检查方必须对**每个条件**给出独立状态，
至少三档：

| 状态 | 含义 | 对门禁的影响 |
|------|------|-------------|
| ✅ 满足 | 已验证，且验证方式可复核 | 计入放行 |
| ⛔ 受阻 | 有明确外部依赖，未完成；写明原因与解阻条件 | 计入不放行，但**可见** |
| ❓ 未验证 | **该验证的没有验证过**，或检查单里根本没有对应条目 | 计入不放行，**且单独告警** |

其中 ❓ 是本次新增的、也是唯一真正新增的东西。

### 2.1 ❓ 与 ⛔ 的区别是本 ADR 的核心

| | ⛔ 受阻 | ❓ 未验证 |
|---|--------|-----------|
| 性质 | **外部依赖**——工程上已尽力 | **内部遗漏**——本可以做完但没做 |
| 例 | 缺代码签名证书 | 从未跑过安装形态冒烟 |
| 解阻责任 | 产品 / 采购 / 外部账号 | 本团队，下一轮就能做完 |
| 是否可延期 | 可（需显式记录与决策） | **不可延期**——它不是「来不及」，是「没做」 |

把两者混为一谈，是**用外部依赖掩盖内部遗漏**的机制。
本次存档查看器就出现过这个效果：如果只看「G4 因签名不通过」，
很容易得出「等买了证书就能发」的结论，而实际上还有三项工程遗留没做。

### 2.2 对门禁条文的影响

`roles.md` §4 的门禁表需要相应改写。以 G4 为例，现状与目标：

**现状**

> G4 = `doc-engineer` 用户文档完成 + `release-engineer` 签名/安装包/更新通道检查单**全绿**

**目标**

> G4 = `doc-engineer` 用户文档完成 **且** `release-engineer` 检查单中
> **每个条目**都给出状态：✅ 已验证 / ⛔ 受阻（须写原因与解阻条件）/ ❓ 未验证。
> 存在任何 ⛔ 或 ❓ 时不通过，但**必须逐项列出**，不得只给聚合结论。

## 3. 备选方案

| 方案 | 做法 | 为何未采用 |
|------|------|-------------|
| A. 保持现状 | 门禁只问全绿与否 | 就是本 ADR 要解决的问题 |
| B. 新增「受阻可放行」档 | 允许带受阻项通过门禁 | 治标。它解决「被签名卡死」，但**不解决**「未验证项被盖住」——反而可能放大它：一旦允许带受阻放行，未验证项更容易混过去 |
| C. 要求检查单「覆盖完整」 | 要求检查单列出所有应验证项 | 方向对，但不够。「列出」不等于「分项给结论」，仍可能把 ⛔ 和 ❓ 混写 |
| D. 门禁加一道独立「验证完备性」核查 | 在门禁前增设一次清单比对 | 成本高，且需要另一份「应验证项清单」，容易与检查单本身漂移 |

**未一并处理的相邻缺口**（此前已登记，本次不动）：

- `roles.md` §3.8 完成标准 > §4 门禁条件，**标准口径不一致**
- 门禁**缺少「受阻」这一档**（无任何阶段性放行机制）

本 ADR 只解决「分项结论」。另两处应在独立 ADR 中处理，
避免一次改多处、无法判断哪一处改动带来了行为变化。
不过需提示：**若将来处理「缺受阻档」，必须与本 ADR 一并考虑**，
否则会出现「允许带受阻放行，但未验证项仍不单独告警」的组合，
那比现状更糟。

## 4. 后果

### 4.1 正面

| # | 后果 |
|---|------|
| 1 | 未验证项与受阻项**不再混淆**，外部依赖不再掩盖内部遗漏 |
| 2 | 门禁结论自带「还差什么、差在谁头上」的清单，移交成本降低 |
| 3 | 审计与复核有了明确的核对对象（「有没有 ❓」），而不是「有没有说谎」 |
| 4 | 本次存档查看器的实际情况可直接验证该设计价值：**3 项 ⛔ + 3 项 ❓**，两者处置路径完全不同 |

### 4.2 负面 / 成本

| # | 后果 | 缓解 |
|---|------|----------|
| 1 | 每道门禁的核对工作量增加（从看聚合结论变成逐条） | 条目数量有限；且检查单本来就是逐条的 |
| 2 | 「完备性」需要判断力——「这条该不该有」无法完全机械判定 | 引入 ❓ 的**误报**，由 orchestrator 抽检裁定；误报可接受，漏报才是问题 |
| 3 | 改了不变层，需按 `AGENTS.md` 走 ADR + 活文档同步 | 本文档即为此而写 |
| 4 | 短期内会让部分门禁看起来「更红」 | 这是**如实反映**，不是新增问题 |

### 4.3 风险

**最大风险是 ❓ 变成新的应付性标记**——什么都标「未验证」，等于没做。

缓解措施：❓ 只允许用于**确实没做过**的事；
若某条目因外部原因无法完成，必须标 ⛔ 并写原因。
两者的区别靠「能不能由本团队独立完成」判定，orchestrator 有权驳回。

## 5. 验证方式

本 ADR 生效后，可用本项目**回溯检验**：

1. 取 `feat/save-inspector` 分支，套用新门禁条文；
2. 预期 G4 结论中出现 **❓ 未验证** 条目，且至少包括：
   - Windows 安装形态冒烟
   - NFR-1 首屏时间
   - NFR-2 大存档表现
3. 若这三条**没有**出现在结论里，则本设计无效，应重新评估。

> 这三条已在本轮补齐，因此回溯检验的样本取自**补齐前**的 `e200c80` 状态。
