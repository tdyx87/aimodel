# ADR-0005：本地 Web UI（不引入 Web 框架）

- 状态：已接受（2026-10-21）
- 相关：`docs/design/contract.md` §7（终端界面）、§8（平台差异）、§5.2（权限模型）

## 背景

终端界面有真实门槛：单键批准、长工具输出刷屏、历史难翻。
用户明确要求「给个 Web UI」。

但本项目有三条硬约束：

1. 语言锁 C99，**依赖只有 libcurl**（NSIS 教训：把可选依赖变成阻塞项拖红了整条 CI）。
2. 极低内存（NFR-1：100 MB）。
3. 平台差异只允许出现在传输层（契约 §8）。

一个「网页版代理」天然需要：HTTP 服务、并发、模板、JSON、SSE。
若引入 Web 框架（哪怕是单文件的 C 框架），就等于引入一条新的依赖链，
而这条链在 CI 上是要在三个平台上都编过的。

## 决策

**自建一个极小的本地 HTTP/SSE 服务，不引入任何第三方库。**

- `src/web_net.c`：平台差异（Windows winsock2 / POSIX socket、线程、互斥量、系统熵）。
- `src/web.c`：协议逻辑（HTTP 解析、SSE、事件/消息通道）。
- `src/web_page.c`：页面内嵌在二进制里（单文件交付，没有「路径不对就白屏」）。
- 依赖：仅 Windows 上的 `ws2_32` 与 `bcrypt`（都是系统 DLL）。

## 理由

- **依赖不变**：多两个系统 DLL 不等于多一条需要维护的第三方依赖链。
- **内存可控**：连接数上限 64、SSE 客户端上限 32、请求体上限 64 KB、
  消息队列 32×8 KB，全是定长。框架的请求对象、路由表、模板缓存都不可控。
- **平台差异仍收在一处**：`web_net.c` 之外没有任何 `#ifdef _WIN32`。
- **页面内嵌**：单文件交付是这个项目的风格。

## 安全取舍（不可协商的四条）

1. **只监听 127.0.0.1**：这个服务能让模型执行命令，绝不能暴露到局域网。
2. **随机令牌**（32 字节系统熵）：URL 里带令牌，没有令牌的请求一律 401。
   没有它，本机任意网页都能驱动你的代理。
3. **校验 Host 头**：挡住 DNS rebinding（恶意网站把域名解析到 127.0.0.1）。
4. **Web 模式下 run_shell 仍需显式 `CAGENT_ALLOW_SHELL=1`**：
   「浏览器里点一下就执行命令」不该是默认状态。

## 后果

- 好处：浏览器里有聊天记录、工具卡片、批准按钮；控制台仍可用（显示同样的内容）。
- 代价：自己实现 HTTP 解析，边界情况要自己管（已实现：请求头上限、请求体上限、
  连接数上限、SSE 客户端上限；未实现：keep-alive 复用、分块编码、压缩）。
- 代价：页面是内嵌字符串，改 UI 要重新编译（可接受：UI 改动不频繁）。
- 后续可考虑：把页面拆成独立静态文件（需要处理「文件从哪来」的问题）。

## 备选与否决理由

- **引入 libmicrohttpd / civetweb**：省掉自己写 socket，但引入新依赖链，
  且在 Windows/MSVC 上的构建问题会重演 NSIS 那次（包源/工具链不匹配拖红 CI）。
- **只做终端改进**：用户明确反馈终端难用；而且「命令面板/补全」只解决一部分问题。
- **Web UI 直接执行工具、无批准**：违反契约 P1/P2，不予考虑。
