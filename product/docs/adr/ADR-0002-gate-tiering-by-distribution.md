# ADR-0002：门禁按分发档位分级，信任要求可分档

## 1. 背景

### 1.1 触发事件

存档查看器 0.1.0 决定按**未签名试用分发**发放。产品决策本身合理：
小范围用户、已知风险、已写明未签名与校验方法。

但门禁流程给不出对应的放行路径：

| 条文 | 要求 | 实际 |
|------|------|------|
| `§3.11` release-engineer 完成标准 | 签名**有效**、更新通道**可用**、检查单全绿 | 两项均未达成 |
| `§4` G4 | 检查单**全绿** | 6 项受阻 |

结果是：G1~G3 全部通过（内部质量没问题），却因为**两条面向外部信任的要求**
被整体拦下，且没有任何「可以发但要注明未签名」的档位可选。

### 1.2 问题的实质：门禁混了两种不同性质的要求

把现有四道门禁拆开看，它们问的根本不是同一类问题：

| 门禁 | 问的是 | 性质 |
|------|--------|------|
| G1 设计 | 需求与设计是否说清楚了 | **内部质量** |
| G2 合入 | 代码是否符合规范 | **内部质量** |
| G3 质量 | 功能是否正确、安全 | **内部质量** |
| G4 发布 | **交给陌生人是否安全** | **外部信任** |

「代码写得好不好」不因为听众是谁而改变 —— 写坏的代码给 5 个人看还是给
500 万人看，坏的程度一样。

但「能不能交给陌生人」**强烈依赖听众**：自己电脑上跑、给几个认识的人试、
放到公网上被任何人下载，信任成本差着几个数量级。

现有条文把这两类要求**压进了同一个 G4 条件**，于是出现了最难受的情况：
内部质量明明过关，却被外部信任要求整体拦下。

### 1.3 不是「没设计」，是「设计自相矛盾」

值得单独指出：框架**已经有**分档所需的机制，只是坏在没人用起来。

| 条文 | 原文含义 |
|------|----------|
| `§3.12` orchestrator 完成标准 | 全部门禁**按序通过或受阻有明确记录** |

`§3.12` 明确允许「受阻但记录清楚」作为完成状态。而 `§4` 与 `§3.11`
要求「全绿」。**同一套框架里，一个说「受阻有记录即可」，另两个说「必须全绿」。**

所以准确的表述不是「缺少分档设计」，而是**已有分档机制，但与全绿要求矛盾，
且从未被使用过**。这决定了修复方式（见 §2）。

## 2. 决策

### 2.1 引入**分发档位**，G4 的信任要求按档位分级

| 档位 | 受众 | 可承受的信任缺失 |
|------|------|-----------------|
| **T0 内部** | 本人 / 本团队 | 无限制。仅本机，不对外 |
| **T1 试用** | 少量已知用户 | **未签名**，但必须：写明未签名 + 提供 SHA256 + 不做自动更新 + 有回退路径 |
| **T2 公开** | 任何人可下载 | 签名有效 + 公证通过 + （T1 的全部要求） |

### 2.2 关键约束：G1~G3 **不随档位变化**

这是本 ADR 最重要的一条，必须写死：

> **档位只放宽 G4 的外部信任要求，绝不放宽 G1~G3 的内部质量要求。**

理由：若允许「开发阶段降低质量门禁」，「开发阶段」会变成垃圾桶——
任何东西都可以说「我们还在开发阶段」来降低标准，且永远可以这么说。

内部质量是内部质量，与听众无关。**档位不改变「做得好不好」，只改变「能给谁」。**

### 2.3 只对 G4 做参数化，不新增门禁

不引入「G4-dev / G4-release」两道门。理由：门禁数量增加会稀释每道门禁的
严肃性，且 `agents.md` 要求门禁「有序、有明确放行条件、不可跳过」——
多一道就多一处可讨论的跳点。

改为：**G4 一道门，但其放行条件按本次声明的档位展开。**

| 声明档位 | G4 放行条件 |
|---------|------------|
| T0 | G1~G3 通过即可；不产出对外产物 |
| T1 | G1~G3 通过 + `doc-engineer` 文档完成 + 检查单逐项状态齐全，**允许存在 ⛔ 但须写明原因与风险**，并产出试用分发说明 |
| T2 | G1~G3 通过 + `doc-engineer` 文档完成 + 检查单**全绿**（含签名有效、更新通道可用） |

### 2.4 档位由谁定、如何防滥用

档位由**产品决策方声明**，且必须满足**可核查的受众定义**：

| 档位 | 受众定义必须具体到 |
|------|------------------|
| T1 | 明确的分发对象与途径（例如「发给 X 个自愿试用的朋友」） |

**防滥用的三条硬约束**：

1. **T1 必须声明受众范围**。写成「发给需要的人」不算定义。
2. **T1 必须有回退记录**（如何撤回）。无更新通道意味着撤回管不了已下载的副本，
   这一风险必须显式记录而非隐含。
3. **档位提升必须重新走 G4**。从 T1 到 T2 不是「顺手升级」，
   需要单独声明、单独裁决。

### 2.5 消除 `§3.12` 与 `§4` 的矛盾

`§3.12` 的「或受阻有明确记录」**予以保留**，但明确其适用层级：

- `§3.12` 的「受阻有记录」说的是**流程可以走完**（orchestrator 可以结项）；
- `§4` 的放行条件说的是**这次发放够不够格**。

两者不是同一层：流程走完 ≠ 允许发放。矛盾之所以存在，是因为
「受阻」被同时读成了这两种意思。本 ADR 把它们分开表述。

## 3. 备选方案

| 方案 | 做法 | 为何未采用 |
|------|------|-------------|
| A. 开发/发布两道门 | 按用户的字面提议，G4 拆成 G4-dev 与 G4-release | **门禁数量增加**，多一处可跳点。且「开发阶段」是个会持续很久的状态，很难界定何时结束——容易变成永久豁免 |
| B. 只用 `§3.12` 现有口子 | 不改设计，强调「受阻有记录即可结项」 | 改动最小，但它**不告诉任何人什么档位可以发**。「有记录就行」与「未签名可以发给陌生人」之间仍无界限，实践中会滑向「什么都记录一下就发了」 |
| C. 不管，发行时人工特批 | 保持现状，每次由决策方单独决定 | 就是已经发生的情况。它的真实成本是：**每次都要重新讨论一遍**，且讨论结论不留痕。0.1.0 这轮就讨论了至少三次 |
| D. 分档（采纳） | G4 放行条件按 T0/T1/T2 展开 | —— |

**B 的问题需要说清**：它看似省事，实则把判断从「规则」退化成「每次重新讨论」，
而没有任何可复用的判据。0.1.0 那三轮讨论（先建议不签名 → 再记录建议 →
最后决定发放）就是这个退化的实证。

## 4. 后果

### 4.1 正面

| # | 后果 |
|---|------|
| 1 | T2 的签名/公证/自动更新要求**没有被削弱**，只是不再错误地施加到 T1 |
| 2 | 分档判据落成文字且可复用，不需每次重新讨论 |
| 3 | `§3.12` 与 `§4` 的矛盾被消解，各自表述层级明确 |
| 4 | 与 ADR-0001 组合后，「未验证」与「不可达」在**任何档位**都不被允许混同 |

### 4.2 负面 / 成本

| # | 后果 | 缓解 |
|---|------|----------|
| 1 | **T1 被滥用为永久档位**：一直发试用版，迟迟不做签名 | 提升需重新裁决 + T1 记录归档可见。**接受此风险**，因为它比「要么买证书要么不发布」的现状更有产出 |
| 2 | **低报档位**：实为公开分发却声明 T1 | 受众定义必须具体可核查（§2.4）；orchestrator 抽检时核对实际分发途径 |
| 3 | 门禁条件变复杂，核对成本上升 | G4 条件表按档位三行写清，不引入额外门禁 |
| 4 | 需修改 `.role-system/` | 走 ADR + 活文档同步；批准前不变更 |

### 4.3 明确不做的事

- **不给 T1 设质量下限**——T1 的 G1~G3 与 T2 完全相同，不打折。
- **不引入「紧急通道」**。降级必须有迹可循，不能有「这次特殊情况」的口子。
- **不自动提升档位**。同一版本不会因为「发了一阵子没人出事」而自动变可信。

## 5. 与 ADR-0001 的关系

两件事，互补，不可互相替代：

| | ADR-0001 分项结论 | 本 ADR 分档 |
|---|---|---|
| 解决的问题 | 未验证项被受阻项盖住 | 高信任要求被施加到低信任场景 |
| 作用层 | **报告层**：如实报告每一项的状态 | **判据层**：不同档位要求不同 |
| 若单独实施 | 看得更清楚，但**仍然什么都不发** | 能发了，但状态仍可能是含混的 |

**组合效果**：任何档位下，⛔（受阻）与 ❓（未验证）都必须逐项可见；
T1 只放宽「能否发给陌生人」，不放松「该验的有没有验」。

**风险提示**：若只采纳本 ADR 而不采纳 ADR-0001，则「声明 T1」容易与
「把未验证项标成受阻」组合使用 —— 两者叠加会显著降低门槛。
**建议两条同时批准。**

## 6. 验证方式

生效后，用本项目回溯检验：

1. 取 `feat/save-inspector` 的 `80461ec`（0.1.0 试用分发时的状态）；
2. 按分档后的条文重判，声明档位为 T1；
3. 预期结论：**放行**，且条件中「签名有效」一条标为
   **「T1 不要求，但须写入分发说明的风险项」**，而不是被隐去；
4. 同时检查分发说明是否含：未签名告知、SHA256、回退路径、受众定义。

若第 3 步的「T1 不要求」最终变成「不用提」，则分档退化为放行橡皮章，本设计无效。
