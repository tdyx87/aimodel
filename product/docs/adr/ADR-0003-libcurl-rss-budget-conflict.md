# ADR-0003：libcurl 的 RSS 代价与 NFR-1 内存预算冲突

- 状态：**已决策（2026-10-19）——采用方案 A，NFR-1 放宽到 100 MB**
- 日期：2026-10-19
- 相关：`docs/design/contract.md`（依赖约束 / NFR-1）

---

## 背景

契约里有两条约束，在实现层面**不可能同时成立**：

| 条款 | 内容 |
|------|------|
| 依赖约束 | 「仅允许 libcurl」作为 HTTPS 传输方案 |
| NFR-1 | 空闲 RSS ≤ **8 MB** |

它们冲突的原因不是代码写得不好，而是 **libcurl 本身的常驻代价**。

## 实测数据

全部为实测，不是估算。

### 1. 我们的代码本身

| 环境 | 峰值 RSS |
|------|----------|
| WSL2 / Ubuntu 18.04 / GCC 9.4 | **0.99 MB** |
| Windows / MSVC 14.16 | 5.43 MB |

`mem_probe` 保持 30 秒、无请求、空载状态。

### 2. libcurl 的加载代价

在 WSL2 上写了一个只做 `dlopen` + `curl_global_init` 的最小程序：

    加载前 RSS : 792 KB
    dlopen+curl_global_init 后 : 6980 KB
    净代价 : 6188 KB = 6.04 MB

### 3. 合起来

| 组成 | RSS |
|------|-----|
| 我们的代码 | 0.99 MB |
| libcurl + TLS 依赖链 | 6.04 MB |
| 基线合计 | ≈ 7.0 MB |
| **CI Ubuntu runner 实测（含 TLS 证书库、解析器、runner 环境）** | **9.40 MB** |

结论：**只要 libcurl 被链接并加载，NFR-1 的 8 MB 就达不到。**

## 为什么这个问题拖到现在才发现

诚实地说：这是我的判断失误。

那个被我当作「NFR-1 已达成」的 5.43 MB，是**在没链接 libcurl 的 Windows 构建上测的**
（`find_package(CURL)` 在本机 NOTFOUND，回退到了内存后端）。
它从来就不包含 libcurl 的代价。

> 把一个「在特定配置下测出的数字」当成「需求已达成」——
> 中间缺了一步验证：**这个数字是在交付配置下测的吗？**

这个教训比 ADR 本身更值得记住。项目里已经栽过三次同类的坑：

| # | 现象 | 真相 |
|---|------|------|
| 1 | Windows 超时用例「通过」 | `sleep` 在 cmd 里不存在，目标分支一次都没跑到 |
| 2 | 告警门禁「零告警」 | grep 只匹配 MSVC 格式，GCC 的 12 条全漏检 |
| 3 | 符号链接用例「通过」 | 链接建在 CWD，工作区里根本没有那个链接 |

三次都是**测试/门禁看上去覆盖了，实际覆盖的是别的东西**。
第四次是**验收数字看上去达标，实际不达标**。

## 三个候选方向（均未采纳，留待决策）

### A. 放宽 NFR-1 ✅ **已采纳**

改为「空闲 ≤ 12 MB / 活跃 ≤ 20 MB」。

- 优点：零实现成本。
- 代价：放弃「极低内存」这个项目的核心卖点。
- 诚实性：必须在 PRD 与用户文档里明确写出这个数字，不能只写在 ADR 里。

### A′. 放宽到 100 MB ← **实际采纳的方案**

2026-10-19 用户决策：内存占用「有点苛刻」，放开到 **100 MB**。

比方案 A 宽松得多。实际影响：

| 项 | 结果 |
|----|------|
| CI 内存门禁 | 恢复全绿（Ubuntu 实测 9.35 MB） |
| 契约 C1/C4/C5 | **不变** —— 放宽的是数字，不是「不许无界增长」的要求 |
| 分层预算（单帧/arena/工具结果/历史/文件读入） | **不变** —— 它们约束单次操作，与池子总大小无关 |
| PRD 定位 | 已改写：不再声称「省 90%+」，差异点转移到默认拒绝、历史明示、单二进制 |

**理由**：100 MB 让所有真实成本（含 libcurl 的 6.04 MB）都能被计入，
指标重新变得**可验证**。一个在交付配置下成立的 100 MB，
比一个只在「没链接 libcurl 的构建」下成立的 8 MB 更有价值。

**必须诚实记录的后果**：100 MB 与同类工具（80~150 MB）**处在同一量级**，
本产品不再有内存上的倍数优势。PRD §1 与 §5.2 已据实改写。

### B. libcurl 改为按需 dlopen

代理启动时不加载 libcurl，真正发起请求时才 `dlopen`。

- 空闲：≈ 1 MB，**保住 NFR-1 的「空闲」指标**
- 请求期间：≈ 7–9 MB
- NFR 需拆成两条：「空闲 ≤ 2 MB / 请求期间 ≤ 12 MB」
- 代价：`transport_curl.c` 改为 `dlsym` 绑定。用到的 curl API 面很小
  （easy handle / setopt / perform / 3 个回调），工作量可控。
- 风险：函数指针签名必须与 curl 头文件一致，需人工核对；
  `curl_global_init` 的参数与 `CURLcode` 布局也要对。
- 附注：这条路的收益只在「长期空闲」时成立。若代理典型用法是
  **持续在线并频繁请求**，空闲指标改善的实际价值有限——
  这一点应在决策前想清楚，不要为指标而指标。

### C. 换更小的传输库

mbedtls 之类，HTTPS 支持自己拼。

- 工作量最大，收益不确定。
- 在这个阶段不推荐。

## 决策前需要回答的问题

1. **典型使用形态是什么？** 长期挂着的交互式会话，还是偶尔跑一次？
   若是前者，B 的收益需要打折评估。
2. **8 MB 这个数字是怎么来的？** 是从用户价值倒推的，还是先有数字再找理由？
3. 预算若放宽，是写进 PRD 面向用户，还是只作为内部实现指标？
