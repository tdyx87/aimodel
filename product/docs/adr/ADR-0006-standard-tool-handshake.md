# ADR-0006：工具结果回灌采用标准工具握手

- 状态：已接受（2026-10-22）
- 相关：`docs/design/contract.md` §4.3（协议适配）、§5.3（回灌形式）、§2.5.6（工具回合不跨输入保留）
- 上游：`docs/HANDOFF.md` §6「高：工具结果标准握手」

## 背景

工具执行完，必须把结果回灌给模型，让它接着往下答。早先的做法是：

1. 把结果包进 `<result>...</result>`，作为一条**尾随 user 消息**发出去；
2. 其后附一句「该工具已执行，请据此继续，不要重复调用同一工具」。

真实服务（GLM-4.6/4.7）实测的故障：模型收到这段「用户消息」后，
会**原样再要一次同一个工具**——因为它看到的是「用户又说话了」，
而不是「你刚才那次调用的结果」。于是同一个写文件请求被反复请求，
用户要一次次批准同一件事。附注的提示句只能缓解，不能根治。

OpenAI 规范对「工具结果」有明确的、带配对语义的表示法：
助手先发一条带 `tool_calls` 的消息，工具结果再以 `role:"tool"` +
`tool_call_id` 逐条回去。模型据此能把结果**挂回**它自己发出的那次调用。

## 决策

**改用标准工具握手**：

- 请求侧新增两种消息形态（`include/cagent/llm.h` 的 `ca_llm_msg`）：
  - 助手携带 `tool_calls`：`{"role":"assistant","content":null,"tool_calls":[...]}`
    （`tool_calls` 是**逐字回带**的原文，见下）
  - 工具结果：`{"role":"tool","tool_call_id":"...","content":"..."}`
- 一轮里每个工具结果**各自独立成一条** tool 消息，按 id 与调用配对。
- 回带块（assistant tool_calls + 各 tool 结果）作为整体，紧随会话历史之后，
  在**当前这次用户输入的循环内**有效。

## 理由

- **根治而非缓解**：配对语义让模型知道这是调用结果，从结构上消除「再要一次」。
- **tool_calls 存原文**：服务端会做一致性校验，`解析→重新序列化` 可能改变字节
  （键序 / 转义 / 数字格式），有被拒风险，且无任何收益。
- **不破坏既有约束**：
  - 依赖方向不变（仍是 core → llm，工具 Schema 仍由 tools 层单点提供）。
  - 内存仍是定长：回带缓冲 `CA_LLM_MAX_TOOL_CALLS × (id + args + name + 余量)`，
    结果文本仍受 `CA_CORE_MAX_RESULT_BYTES`（256 KB）封顶。
  - 工具回合**仍不跨用户输入保留**（§2.5.6）：握手只在一次输入内有效，
    历史里依旧只有 user/assistant 文本。

## 后果

- **好处**：真实服务上同一工具的重复请求显著减少；用户批准负担下降；
  契约 §5.3 的「已知局限」被消除。
- **代价**：结构体 `ca_llm_msg` 增两个字段 → **所有填充它的地方都要同步更新**。
  本 ADR 落地时就踩到了这个坑：`ca_session_export` 漏置新字段，
  未初始化指针被序列化器当 tool_calls 解引用 → 段错误（详见
  `docs/audit/2026-10-22-cpp-implementer-tool-handshake.md` §4）。
  已用「导出必须置 NULL」的测试钉住不变量。
- **代价**：请求体略大（回带 tool_calls 与逐条结果），`mem_load --turns 500`
  峰值由 7.71 MB 升至 8.02 MB，远在 100 MB 预算内。
- **约束（新增硬要求）**：回带块**不可被部分丢弃**。历史淘汰只允许发生在
  回带块之前；拆散它会制造「有结果无调用」的 400，且只在长上下文下复现。
- **约束（新增硬要求）**：`tool_calls` 必须是**数组** `[...]`。
  拼成对象 `{"id":...}` 会被服务端 400。这条是**实现期实测踩到**的
  （见审计 §4 的「三个真 bug」之 2），不是推测。

### 顺带修掉的既有缺陷（与本 ADR 同批落地）

1. **回灌上限与请求体容量脱节**：回灌缓冲固定 256 KB，而请求体默认也是 256 KB
   （还能配到 16 KB 下限）。工具结果填满回灌缓冲就**必然**装不进请求体 →
   整轮失败；把 context 配小一点，代理直接不可用。
   改为**由请求体容量倒推**回灌配额（`ca_core.results_cap`）。
   截断器的职责是「保证请求还发得出去」，不是「尽量多塞」。
2. **截断路径不写 NUL 结尾** → 序列化器按 C 字符串读，越界读。
3. **截断时可能回缩 `results_len`** → 某条消息的长度下溢成天文数字，越界读。

## 备选与否决理由

- **保留尾随 user 消息 + 加强提示句**：已证明只缓解不根治；且把「工具结果」
  混同于「用户发言」，语义本身就是错的。
- **只回带 tool_calls、结果仍走 user**：服务端要求每条 tool_calls 都有
  对应的 `role:"tool"` 结果，否则 400。不可行。
- **把 tool_calls 解析成结构体再序列化**：徒增一次可能漂移的编解码，无收益（D1）。
